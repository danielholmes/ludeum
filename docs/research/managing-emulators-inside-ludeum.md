## A. DuckStation (current master)

### A1. How the data directory is chosen on macOS

Entry point: `QtHost::InitializeFoldersAndConfig` calls `Core::SetCriticalFolders` (https://github.com/stenzek/duckstation/blob/master/src/duckstation-qt/qthost.cpp, ~line 852). The directory logic itself lives in `src/core/core.cpp`, not qthost:

`Core::SetCriticalFolders` (https://github.com/stenzek/duckstation/blob/master/src/core/core.cpp, ~line 89) = `SetAppRootAndResources` then `SetDataRoot`.

**AppRoot and Resources** (`Core::SetAppRootAndResources`, core.cpp ~line 108):

```cpp
const std::string program_path = FileSystem::GetProgramPath(error);
...
EmuFolders::AppRoot = Path::Canonicalize(Path::GetDirectory(program_path));

#ifdef __APPLE__
  // MacOS resources are inside the app bundle. We might not be running in a bundle.
  const std::optional<std::string> bundle_path = CocoaTools::GetBundlePath();
  if (bundle_path.has_value())
    EmuFolders::Resources = Path::Combine(bundle_path.value(), "Contents/Resources");
  else
    EmuFolders::Resources = Path::Combine(EmuFolders::AppRoot, "resources");
#else
  EmuFolders::Resources = Path::Combine(EmuFolders::AppRoot, "resources");
#endif
```

`FileSystem::GetProgramPath` on `__APPLE__` uses `_NSGetExecutablePath` (https://github.com/stenzek/duckstation/blob/master/src/common/file_system.cpp, ~line 3062; note it calls `realpath` but then returns the *unresolved* `buffer`, so symlinks are not resolved). So **AppRoot = the directory containing the Mach-O executable = `DuckStation.app/Contents/MacOS`**, not the folder next to the .app. `CocoaTools::GetBundlePath` returns `[NSBundle mainBundle]` only when `CFBundlePackageType == APPL` (https://github.com/stenzek/duckstation/blob/master/src/common/cocoa_tools.mm, ~line 88).

**DataRoot** (`Core::SetDataRoot`, core.cpp ~line 142):

```cpp
  std::string_view real_approot = EmuFolders::AppRoot;
#ifdef __linux__
  if (const char* appimage_path = std::getenv("APPIMAGE"))
    real_approot = Path::GetDirectory(appimage_path);
#endif
  // Check whether portable.ini exists in the program directory.
  if (FileSystem::FileExists(Path::Combine(real_approot, "portable.txt").c_str()) ||
      FileSystem::FileExists(Path::Combine(real_approot, "settings.ini").c_str()))
  {
    EmuFolders::DataRoot = std::string(real_approot);
    return true;
  }
  ...
#elifdef __APPLE__
  static constexpr char MAC_DATA_DIR[] = "Library/Application Support/DuckStation";
  const char* home_dir = getenv("HOME");
  if (home_dir)
    EmuFolders::DataRoot = Path::RealPath(Path::Combine(home_dir, MAC_DATA_DIR));
  else
    Error::SetStringView(error, "HOME environment variable is not set.");
#endif
```

Answers:

- **Where `portable.txt` must be on macOS:** inside the bundle at **`DuckStation.app/Contents/MacOS/portable.txt`** (the executable's directory). Next to the .app or in `Contents/Resources` does nothing. An existing **`settings.ini` in `Contents/MacOS` also triggers portable mode** (same check). In portable mode `DataRoot = Contents/MacOS`, so `settings.ini`, `savestates/`, `memcards/` etc. are then written inside the bundle, which breaks the bundle's code-signature seal (see C3). The README only describes the Windows case ("create an empty file named `portable.txt` in the same directory as the DuckStation executable", https://github.com/stenzek/duckstation/blob/master/README.md#user-directories).
- **Env var / flag to set the data dir:** none. The only env vars read in the directory code are `APPIMAGE` (Linux only), `XDG_CONFIG_HOME` (Linux only; note the code reads `XDG_CONFIG_HOME` while the README says `$XDG_DATA_HOME/duckstation`) and `HOME`. The full CLI list (`QtHost::PrintCommandLineHelp`, qthost.cpp ~line 3297, and the `CHECK_ARG` parse) is: `-help -version -batch -nogui -bios -fastboot -slowboot -resume -state <n> -statefile <f> -exe <f> -fullscreen -nofullscreen -bigpicture -setupwizard -earlyconsole -updatecleanup --`. No `-portable`, `-settings`, `-datadir` or similar. Commit `ffd6726a59c509efe1286ce43ad2369603a30621` (2025-04-03, "Qt: Drop -settings/-portable CLI parameters", https://github.com/stenzek/duckstation/commit/ffd6726a59c509efe1286ce43ad2369603a30621) says: "-portable is redundant as the presence of settings.ini in the AppRoot will trigger it anyway ... It was also broken anyway for a long time, and nobody complained." Nothing replaced them.
- **`$HOME` is honoured on macOS:** yes, DataRoot is literally `getenv("HOME") + "/Library/Application Support/DuckStation"`, passed through `Path::RealPath`. Launching DuckStation with a modified `HOME` therefore relocates the whole data root (and `settings.ini`, which is `Path::Combine(EmuFolders::DataRoot, "settings.ini")`, `Core::GetBaseSettingsPath`, core.cpp ~line 259). Caveat: Qt/Cocoa and macOS frameworks also read `HOME` for their own purposes (caches, `NSUserDefaults` domain lookup) — the Qt frontend does use `QSettings` in one place (`gamelistsettingswidget.cpp:20`), **unverified** what it stores or where under a modified HOME.
- **`XDG_DATA_HOME` on macOS:** not honoured; it is only consulted on `__linux__` (and as `XDG_CONFIG_HOME` at that). `QStandardPaths` is not used for the data root.
- The Qt frontend's macOS `Info.plist` (https://github.com/stenzek/duckstation/blob/master/src/duckstation-qt/Info.plist.in) sets `CFBundleIdentifier = com.github.stenzek.duckstation`, registers document types `bin cue img chd m3u psexe psf` as Viewer, `LSApplicationCategoryType = public.app-category.games`, and no `LSUIElement` / `LSMultipleInstancesProhibited`.

### A2. `[Folders]` keys in `settings.ini`

Source: `EmuFolders::SetDefaults`, `EmuFolders::LoadPathFromSettings`, `EmuFolders::LoadConfig`, `EmuFolders::Save` in https://github.com/stenzek/duckstation/blob/master/src/core/settings.cpp (~lines 2985–3075). `Settings::FOLDERS_SECTION_NAME = "Folders"`, `MEMORY_CARDS_SECTION_NAME = "MemoryCards"`, `BIOS_SECTION_NAME = "BIOS"`.

Resolution rule (quoted):

```cpp
std::string EmuFolders::LoadPathFromSettings(const SettingsInterface& si, const std::string& root, const char* section,
                                             const char* name, const char* def)
{
  std::string value = si.GetStringValue(section, name, def);
  if (value.empty())
    value = def;
  if (!Path::IsAbsolute(value))
    value = Path::Combine(root, value);
  value = Path::RealPath(value);
  return value;
}
```

So **relative paths are resolved against `DataRoot`**, absolute paths are used as-is (then `RealPath`'d, i.e. symlinks resolved). `EmuFolders::Save` writes them back with `Path::MakeRelative(x, DataRoot)`. `Path::MakeRelative` (file_system.cpp) walks components and, as soon as the two absolute paths share at least one leading component (always true on macOS, `/Users`), emits a `..`-relative path. So a folder chosen in the UI such as `~/Library/CloudStorage/Dropbox/Ludeum/savestates` is persisted as `../CloudStorage/Dropbox/Ludeum/savestates` relative to `~/Library/Application Support/DuckStation`. A hand-written absolute path in `settings.ini` also works (it is used as-is on load) and stays absolute until the Settings UI re-saves the folders section.

The crash-dump directory is `DataRoot` itself (`CrashHandler::SetWriteDirectory(EmuFolders::DataRoot)`); `settings.ini`, the game list cache, play-time, custom properties and crash dumps live in `DataRoot` and cannot be redirected individually (the `ffd6726a` commit message makes the same point).

### A3. Licence

- `LICENSE` file is **Creative Commons Attribution-NonCommercial-NoDerivatives 4.0 International** (https://github.com/stenzek/duckstation/blob/master/LICENSE, line 1). GitHub's API reports `license.spdx_id = NOASSERTION`.
- **When it changed from GPLv3:** commit `7f4e5d55db` "Misc: Update copyright headers", 2024-09-01 (https://github.com/stenzek/duckstation/commit/7f4e5d55db). Its diff for `LICENSE` is `@@ -1,674 +1,403 @@`, removing "GNU GENERAL PUBLIC LICENSE Version 3, 29 June 2007" and adding the CC text. (The README wording about CC was added in README commits of August 2024, `e8693ed10f` 2024-08-12 / `1e8ca51f44` 2024-08-18 — **unverified** which of the two, I did not diff them.)
- README's own words (https://github.com/stenzek/duckstation/blob/master/README.md):
  - Line 76: "As per the terms of CC-BY-NC-ND, redistribution of **unmodified releases and code** is permitted. However, we would prefer if you linked to https://www.duckstation.org/ instead. Please note that pre-configured settings and packages are considered modifications."
  - Lines 285–287 ("Contributing and Forks"): "As per the terms of CC-BY-NC-ND, you may redistribute **unmodified** versions of this repository, and the compiled binaries. This includes GitHub forks without any changes. **You are not permitted to publish modified versions of this repository.**" and "Please note that "patches", both binary and source are still considered derivative works, since they literally include the original code as part of the patch."
  - The in-app unofficial-build warning (autoupdaterdialog.cpp ~line 175): "DuckStation is licensed under the terms of CC-BY-NC-ND-4.0, which does not allow modified builds to be distributed."
- The licence text itself (LICENSE, Section 2a1): grants the right to "reproduce and Share the Licensed Material, in whole or in part, for NonCommercial purposes only" and to "produce and reproduce, but not Share, Adapted Material for NonCommercial purposes only". "Share" = "provide material to the public" (Section 1i). "NonCommercial means not primarily intended for or directed towards commercial advantage or monetary compensation" (1h).
- What this means for the three cases (my reading of the licence text + README; not legal advice):
  - **Redistributing the unmodified binary** (e.g. a zip of the official `DuckStation.app`): permitted non-commercially, with attribution; the README explicitly says so but prefers a link.
  - **Bundling the unmodified .app inside another app**: nothing in the licence forbids aggregating an unmodified copy, but the README states "pre-configured settings and packages are considered modifications". A Ludeum build that ships `DuckStation.app` with a `portable.txt`/`settings.ini` injected into `Contents/MacOS` is, by the author's stated reading, a modified package. A private, never-published copy on your own machine is not "Sharing" at all, so the licence does not constrain it (the licence only governs providing material "to the public").
  - **Automated download of release binaries**: not addressed by the licence or README; it's just downloading from GitHub Releases, which the README describes as the intended channel. The README does say older releases are only at https://github.com/duckstation/old-releases/releases because "The main releases page is limited to the last 30 releases due to automatic updater limitations" (line 80).

### A4. macOS releases, Homebrew, auto-updater, signing

- **Tags:** GitHub Releases uses the rolling tags `latest` ("Latest Rolling Release", published 2026-10-25) and `preview` ("Latest Preview Build", prerelease, 2026-10-27), plus versioned tags like `v0.1-12083` (2026-10-13), `v0.1-11894`, `v0.1-11826`. Source: `gh api repos/stenzek/duckstation/releases` (https://github.com/stenzek/duckstation/releases, https://github.com/stenzek/duckstation/releases/tag/latest, https://github.com/stenzek/duckstation/releases/tag/preview). `latest` is built from the `dev` branch and `preview` from `master` (macos-build.yml "Tag as Stable Release ... refs/heads/dev", https://github.com/stenzek/duckstation/blob/master/.github/workflows/macos-build.yml).
- **macOS asset:** exactly one, **`duckstation-mac-release.zip`** (~96 MB), a universal x86_64+arm64 bundle, `MACOSX_DEPLOYMENT_TARGET=13.3` (macos-build.yml lines 61–66). README: "macOS Ventura (13.3) is required, as this is also the minimum requirement for Qt." Download URL pattern: `https://github.com/stenzek/duckstation/releases/download/latest/duckstation-mac-release.zip` (README line 141). The zip contains `DuckStation.app/` at the top level (`zip -9 -r duckstation-mac-release.zip DuckStation.app/`).
- **Signing/notarization:** the CI step is `codesign -s - --deep -f -v DuckStation.app` (macos-build.yml line 65), i.e. **ad-hoc signed, not Developer-ID signed, not notarized**. README line 150: "Apple requires code signing for apps to be run without warnings, and I do not have a code signing certificate since a yearly cost is out of the question for a project which brings in zero revenue." README (lines 144–149) tells users to use System Settings → Privacy & Security → "Open Anyway".
- **Homebrew cask:** none. `formulae.brew.sh/cask/duckstation` 404s, `Casks/d/duckstation.rb` does not exist in `Homebrew/homebrew-cask`, a code search for `duckstation` in that repo returns 0 results, and local `brew info --cask duckstation` says "No Cask with this name exists" (checked 2026-10-28).
- **Auto-updater on macOS:** yes, it applies. `autoupdaterdialog.cpp` defines `UPDATER_ASSET_FILENAME "duckstation-mac-release.zip"` under `#elif defined(__APPLE__)` (line 80–81) and has a full `__APPLE__` `processUpdate` (line ~858): it resolves the non-translocated bundle path (`CocoaTools::GetNonTranslocatedBundlePath`), requires the app to be a `.app` bundle, uses `<bundle>/Contents/Resources/Updater.app` to unpack, stages the zip at `<DataRoot>/update.zip` and `<DataRoot>/UPDATE_STAGING`, then launches `Updater.app` with `(parent pid, zip, staging dir, bundle path)` which replaces the bundle in place. Channels (lines 110–111): `latest` = "Stable Releases", `preview` = "Preview Releases"; the default channel is baked at build time via `src/scmversion/tag.h` (`UPDATER_RELEASE_CHANNEL`, `UPDATER_RELEASE_IS_OFFICIAL 1`, written by CI).
- **Disabling it via `settings.ini`:** section `[AutoUpdater]` (`CONFIG_SECTION_NAME = "AutoUpdater"`), key **`CheckAtStartup`** (bool, default true; `MainWindow::startupUpdateCheck` returns early when false, mainwindow.cpp ~line 3154), **`UpdateTag`** (string, `latest`/`preview`), **`LastVersion`** (SHA of a skipped update). `QtHost::SetDefaultSettings` writes `CheckAtStartup = true` unless `ignore_user_prefs` (qthost.cpp ~line 950). The manual "Check for Updates" menu item still works when `CheckAtStartup` is false. Unofficial builds (no `tag.h` or `UPDATER_RELEASE_IS_OFFICIAL` unset) show the "You are not using an official release!" warning instead.
- Consequence for nesting: a nested `DuckStation.app` can update itself in place (it replaces its own bundle path), which would invalidate any outer-bundle seal; set `[AutoUpdater] CheckAtStartup = false` in the managed `settings.ini` if Ludeum manages the copy.

### A5. Single instance?

- **No single-instance enforcement.** There is no `QLocalServer`/`QLockFile`/`QSharedMemory`/"already running" logic anywhere in `src/duckstation-qt` or `src/core/core.cpp` (grep over the clone), no `LSMultipleInstancesProhibited` in `Info.plist.in`, and **no `QFileOpenEvent` handler** (grep), so the Qt frontend does not react to a macOS "open document" Apple event either.
- Behaviour of a second launch with a ROM:
  - If you exec the binary directly (`DuckStation.app/Contents/MacOS/DuckStation /path/rom.cue`) or `open -n -a DuckStation.app --args ...`, you get a **second independent process** that parses its own command line and boots the ROM; both processes share the same `DataRoot`/`settings.ini` (last writer wins; **unverified** whether anything guards concurrent `settings.ini` writes).
  - If you use `open -a DuckStation.app rom.cue` (without `-n`) while it is already running, Launch Services delivers the file to the *existing* instance as an open-document event (standard macOS behaviour, Apple's `open(1)`); since DuckStation has no `QFileOpenEvent` handler, the expectation is that **nothing happens** in the running instance (**unverified** by running it; inferred from absence of handler).

## C. macOS nested application bundles

(Researched by a delegated agent against Apple documentation — read through developer.apple.com's JSON data endpoints since the HTML is JS-rendered — Apple Developer Forums posts by DTS staff, Qt docs, and project repos. "Local observation" = inspection of this Mac with `lsregister -dump`, `codesign`, `mdfind`; evidence, not documentation.)

### C1. Where a nested .app may live; does it keep its own signature?

**Valid locations.** Apple's "Placing content in a bundle" (https://developer.apple.com/documentation/bundleresources/placing-content-in-a-bundle) table for macOS: main executable → `Contents/MacOS/`; resources → `Contents/Resources/`; frameworks/dylibs → `Contents/Frameworks/`; app extensions/plug-ins → `Contents/PlugIns/`; **"help app, helper tool" → `Contents/MacOS/` and `Contents/Helpers/`**; XPC services → `Contents/XPCServices/`; privileged helper → `Contents/Library/LaunchServices/`; Service Management login item → `Contents/Library/LoginItems/`. Quotes: "Bundles can also contain other bundles; for example, an app may contain an app extension." / "Code content is either executable code, like a helper tool, or another bundle that contains executable code" / "If you put content in the wrong location, you may encounter hard-to-debug code signing and distribution problems ... incorrectly placed code might work during day-to-day development, but might cause problems during notarization." / "Each code location must contain a flat list of code content." `Contents/Resources` is not a code location; `Contents/Applications` is not documented at all.

TN2206 (https://developer.apple.com/library/archive/technotes/tn2206/_index.html), Table 3, lists the same: `Contents/MacOS` and `Contents/Helpers` = "Helper apps and tools". "These places are expected to contain **only** code." / "putting code into other places will cause it to be sealed as data (resource) files. This causes this code to be sealed twice ... Also, this can break the outer signature of apps that use their own update mechanisms to replace nested code." Scripts (non-Mach-O) go in `Contents/Resources`.

Code Signing Guide "Signing Code Manually" (https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html): "Everything in an application bundle that is not explicit code (either nested code bundles or the main executable) is a resource, and all resources are signed." / "Do not use custom subdirectories inside the code nesting directories".

**Own signature kept: yes.** TN2206: "From Mavericks onwards, signatures record nested code by its code signature and embed that information in the (outer) signature's resource envelope, recursively ... all nested code **must already be signed correctly** or the signing attempt will fail." / "nested code can be replaced with equivalent (conforms to the designated requirement) nested code without disturbing the outer signature." TN3126 "Inside Code Signing: Hashes" (https://developer.apple.com/documentation/technotes/tn3126-inside-code-signing-hashes): the outer `CodeResources` `files2` entry for nested code holds "the code directory hash of the nested code" and "the designated requirement (DR) of that nested code"; "In theory this lets you update the nested code with a new version, as long as it has the same DR. In practice, this facility is not used in standard deployment workflows and is now deprecated." / "Nested code references are only used on macOS." So a nested .app in `Contents/Helpers` keeps its own signature and notarization ticket (if any); the outer seal only records its cdhash + DR. A nested .app in `Contents/Resources` is instead hashed file-by-file as a resource ("sealed twice").

"Embedding nonstandard code structures in a bundle" (https://developer.apple.com/documentation/xcode/embedding-nonstandard-code-structures-in-a-bundle): "A bundle is a read-only structure ... modifying your app's bundle isn't supported because it breaks the seal on the app's code signature" — relevant because DuckStation's in-app updater rewrites its own bundle (A4) and portable mode writes data into `Contents/MacOS` (A1).

### C2. Launch Services registration, Spotlight, Open With

- Launch Services Programming Guide (https://developer.apple.com/library/archive/documentation/Carbon/Conceptual/LaunchServicesConcepts/LSCConcepts/LSCConcepts.html): "The Finder automatically registers all applications as it becomes aware of them, such as when they are dragged onto the user's disk or when the user navigates to a folder containing them." / "The Open With pane ... contains a pop-up menu listing all known applications in the Launch Services database that claim to accept the selected item."
- **Local observation:** `lsregister -dump` on this Mac shows 163 nested apps registered regardless of location — e.g. `/Applications/Dolphin.app/Contents/Helpers/Dolphin Updater.app`, `/Applications/Docker.app/Contents/MacOS/Docker Desktop.app`, Electron `Contents/Frameworks/* Helper.app`, and **`/Applications/DuckStation.app/Contents/Resources/Updater.app`** (identifier `com.github.stenzek.duckstation.updater`, flags `launch-disabled`). Spotlight (`mdfind "kMDItemContentType == 'com.apple.application-bundle'"`) returned no nested third-party apps; the only nested hits were Finder's own `Contents/Applications/*.app`.
- Apple DTS (Kevin Elliott) in https://developer.apple.com/forums/thread/806244 (2025–26), to a developer whose `Contents/Applications/HelperApp.app` started showing in Tahoe's Spotlight app launcher: "Why are you using "/Contents/Applications/"? That's not one of our documented locations ... I think we started using it so that it WOULD be indexed. Have you tried storing these components in a different directory, specifically "Contents/Helpers"?" The OP confirmed: "Use **Contents/Helpers** instead of **Contents/Applications** to get the app out of the Spotlight app launcher on Tahoe."
- **Open With / duplicate app:** governed by the nested app's `CFBundleDocumentTypes` and `LSHandlerRank` (https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/CoreFoundationKeys.html: `LSHandlerRank` `None` = "this app is never selected to open files of this type"). DuckStation's `Info.plist` declares `bin cue img chd m3u psexe psf` as Viewer with no `LSHandlerRank` (A1), so a registered nested copy would be a second "DuckStation" candidate in Open With for those extensions (**unverified** by test; inferred from the LS guide rule). `LSUIElement` / `LSBackgroundOnly` (https://developer.apple.com/documentation/bundleresources/information-property-list/lsuielement) only hide the Dock/Force Quit presence; Apple documents no key that opts a bundle out of LS registration. Editing the nested DuckStation's `Info.plist` would break its signature and count as a "modification" under its licence (A3).

### C3. Signing: re-sign or not; Gatekeeper for an ad-hoc, local-only outer app

- **No same-identity rule for launching nested apps.** Apple does not document that nested code must share the outer identity; the outer seal just records the nested cdhash + DR (C1). Team-ID matching is a *library validation* rule for loading code into your process, not for launching another app: Quinn, https://developer.apple.com/forums/thread/706437 "If library validation is enabled on an executable, the trusted execution system only allows the process to load code signed by Apple or with the same Team ID as the executable." (inference: `NSWorkspace`-launching a nested .app is not library loading).
- **Local verification:** `codesign -dvv /Applications/DuckStation.app` → `Signature=adhoc`, `TeamIdentifier=not set`; its nested `Contents/Resources/Updater.app` is `adhoc,linker-signed`; `codesign --verify --deep --strict --verbose=2 /Applications/DuckStation.app` → "valid on disk ... satisfies its Designated Requirement". So `--deep --strict` accepts ad-hoc nested code; it checks validity, not identity. An ad-hoc DuckStation.app can therefore sit unchanged inside an ad-hoc-signed Ludeum.app, provided it is in a code location and signed before the outer app is signed ("Sign code from the inside out", https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac; use `-f` when re-signing already-signed code).
- **`--deep` is deprecated for signing.** `codesign(1)`: "--deep (DEPRECATED for signing as of macOS 13.0) ... Beware: All signing options will be applied, in turn, to all nested content. This is almost never what you want." It only finds code in `Contents/{Frameworks,SharedFrameworks,PlugIns,Plug-ins,XPCServices,Helpers,MacOS,Library/Automator,Library/Spotlight,Library/LoginItems}`. Apple: "Don't pass the `--deep` option to `codesign` when you sign code" (https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac, "Avoid deep code signing"); Quinn "`--deep` Considered Harmful" https://developer.apple.com/forums/thread/129980. For *verification* it is fine and matches Gatekeeper: `codesign -vvv --deep --strict` (https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution); TN2206: "Gatekeeper always performs `--deep` style validation." Note DuckStation's own CI uses exactly the deprecated form (`codesign -s - --deep -f -v DuckStation.app`, A4).
- **Gatekeeper when nothing is distributed:** Quinn, "Resolving Trusted Execution Problems" https://developer.apple.com/forums/thread/706442: "running a quarantined app always invokes Gatekeeper" / "The exact circumstances under which it runs Gatekeeper is not documented and changes over time" / "Unix-y networking tools, like `curl` and `scp`, don't quarantine the files they download. Unix-y unarchiving tools, like `tar` and `unzip`, don't propagate quarantine". "Resolving Gatekeeper Problems" https://developer.apple.com/forums/thread/706379: "Gatekeeper requires that your app be notarised. If not, it will block the execution of your app with a generic, user-level message." Apple never states the converse ("no quarantine ⇒ no check"). Practical consequence: a browser-downloaded `duckstation-mac-release.zip` carries `com.apple.quarantine` (local: `/Applications/DuckStation.app` has `com.apple.quarantine: 01c1;…;Chrome;`) and Finder-unzipped contents inherit it; copying that bundle into Ludeum.app or Application Support with the xattr intact means its first launch is blocked until "Open Anyway" (the flow DuckStation's README documents). Fetching with `curl` + `unzip` (or `xattr -d com.apple.quarantine`) avoids both the block and App Translocation (C4).
- TN3127 (requirements, https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) and TN3161 (certificates, https://developer.apple.com/documentation/technotes/tn3161-inside-code-signing-certificates) say nothing specific about nesting; an ad-hoc DR is cdhash/identifier-based and has no Team ID.

### C4. Qt apps nested inside another bundle; App Translocation

- Qt resolves everything relative to **its own** executable/bundle, never the outer bundle or cwd: `qt.conf` is looked up "on Apple platforms, in the Resource directory inside the application bundle, for example `assistant.app/Contents/Resources/qt.conf`", otherwise "in the directory containing the application executable"; "On macOS, the `Prefix` is relative to the `Contents` in the application bundle" and "`application.app/Contents/PlugIns/` is the default location for loading Qt plugins" (https://doc.qt.io/qt-6/qt-conf.html). `QCoreApplication::applicationDirPath()` "On macOS and iOS this will point to the directory actually containing the executable, which may be inside an application bundle" (https://doc.qt.io/qt-6/qcoreapplication.html). macOS deployment: "the best location is to put them under Contents/Plugins"; `macdeployqt` "By default, ad-hoc signing (`-codesign=-`) is used" and uses `@executable_path` (https://doc.qt.io/qt-6/macos-deployment.html). DuckStation's source `qt.conf` is an empty file and the shipped bundle has no `qt.conf` (local observation), with `Contents/PlugIns/{imageformats,platforms,styles}` and Qt dylibs in `Contents/Frameworks` — i.e. the Qt defaults. Conclusion: nesting location is irrelevant to Qt plugin lookup (**unverified** by actually running DuckStation from a nested path).
- **App Translocation** (Quinn, "App Translocation Notes" https://developer.apple.com/forums/thread/724969): "When you run a newly downloaded app, the system executes the app from a randomised path." / "The exact circumstances where the system translocates an app is not documented and has changed over time." / "There is no supported way to detect if your app is being run translocated." Apple "Packaging Mac software for distribution" (https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution): translocation happens when "The person opens your app without moving it to a different location"; "Gatekeeper doesn't translocate your app's path" once the user moves it with Finder. Quinn https://developer.apple.com/forums/thread/732370: "App translocation and quarantine are different things, albeit related." / "we only remove app translocation if the user moves the app using the Finder." DuckStation's updater and PCSX2 explicitly call `GetNonTranslocatedBundlePath` for this reason (A4, B). A quarantined DuckStation.app launched from Application Support could be translocated to a read-only random path; stripping quarantine avoids it. How translocation treats a nested .app inside a non-quarantined outer bundle is **unverified** (undocumented).

### C5. Real examples

(i) Apps shipping nested helper/third-party .apps:
- **Sparkle** (https://sparkle-project.org/documentation/sandboxing/): ships `Sparkle.framework/Versions/B/Updater.app`, `Autoupdate`, `Installer.xpc`, `Downloader.xpc`, "signed with an ad-hoc signature and Hardened Runtime enabled"; host apps re-sign on archive/export; "please do not add `--deep` to `OTHER_CODE_SIGN_FLAGS`".

- **DuckStation** nests `Contents/Resources/Updater.app` (https://github.com/stenzek/duckstation/blob/master/src/updater/CMakeLists.txt) — a non-code location per Apple's table; linker-signed ad-hoc, sealed as a resource; `--deep --strict` still verifies.
- Local observations: `Docker.app/Contents/MacOS/Docker Desktop.app`, `Firefox.app/Contents/MacOS/{updater,plugin-container,...}.app`, `Claude.app/Contents/Helpers/Claude iOS Sim.app` (`LSBackgroundOnly`), Electron `Contents/Frameworks/<App> Helper.app`, `1Password.app/Contents/Library/LoginItems/*.app`, `Xcode.app/Contents/Applications/*` (Apple's own precedent for independently launchable nested apps, per the DTS thread). **Steam Helper**: no primary Valve doc found — **unverified**.

(ii) Launchers that download emulators into a managed folder:

- **RetroDECK** (https://github.com/RetroDECK/RetroDECK, GPL-3.0, Linux Flatpak): bundles emulators inside the Flatpak. Its licences page (https://retrodeck.readthedocs.io/en/latest/wiki_credits_social/donations-licenses/) tabulates per-component licences and says "We also list third-party software that we cannot include in RetroDECK because it is proprietary or otherwise incompatible with our licensing requirements." Its "What's included" page (https://retrodeck.readthedocs.io/en/latest/wiki_about/what-is-included/) lists **DuckStation under "Legacy Components"** — components "no longer actively supported" because of "licensing changes that prevent further updates", provided "as-is". This is the clearest real-world consequence of DuckStation's CC BY-NC-ND switch for a bundling distributor.
- **Playnite** (https://github.com/JosefNemec/Playnite, MIT, Windows): does **not** download emulators; its "Download Emulators…" dialog says "You can download emulator installers from their websites. Once you have the emulators installed (manually), you can import them" (`LocSource.xaml`, `LOCEmuDownloadDescription`); the DuckStation definition only carries `Website: 'https://github.com/stenzek/duckstation'` and `StartupArguments: '-batch -fullscreen "{ImagePath}"'`.
- **LaunchBox** (Windows, proprietary): "LaunchBox can download supported emulators directly, extract them to the correct location" via official emulator plugins, matrix includes DuckStation (https://launchbox.featurebase.app/help/articles/1605395-plugins-overview). No licensing statement on that page.
- **OpenEmu** (https://github.com/OpenEmu/OpenEmu, macOS): cores are downloaded at runtime, not shipped: `OpenEmu-Info.plist` `OECoreListURL = https://raw.github.com/OpenEmu/OpenEmu-Update/master/oecores.xml`, `OEBundlePath = ~/Library/Application Support/OpenEmu/Cores/`; `CoreUpdater.swift`/`CoreDownload.swift` fetch Sparkle-style appcasts whose enclosures are GitHub release zips (e.g. https://raw.githubusercontent.com/OpenEmu/OpenEmu-Update/master/bsnes_appcast.xml → `BSNES_115.zip`) and unzip them into that folder. **Bottom line for C:** the documented pattern is `Contents/Helpers` (or `Contents/MacOS`); the nested app keeps its own ad-hoc signature; sign inside-out without `--deep`; nested apps get LS-registered wherever they sit and DuckStation's document claims would surface it in Open With; Qt doesn't care where it's nested; the real hazards are quarantine/translocation on the downloaded zip, DuckStation's self-updater and portable mode writing into the bundle (seal-breaking), and the licence's "pre-configured settings and packages are considered modifications" if Ludeum is ever shared. No verified macOS launcher ships a third-party emulator .app inside its bundle; the macOS precedent (OpenEmu) downloads into Application Support.

## D. Dropbox and live emulator data

(Researched by a delegated agent against help.dropbox.com, dropbox.tech, Apple File Provider docs and project trackers; DuckStation write-path claims re-checked by me in the clone.)

### D1. Dropbox's documented behaviour: change detection, open files, conflicted copies, app data, online-only

- **Conflicted copies** (https://help.dropbox.com/organize/conflicted-copy): "A conflicted copy is a file that Dropbox creates when multiple people edit the same file at the same time." Listed causes: "Two users change the same file at the same time." / "Someone edits a file offline while someone else edits the same file." / "A file is left open on another user's computer, which Dropbox saves as a new edit" ("especially common when using applications with an auto-save feature"). "The last version saved will always appear as the conflicted copy." All three causes are two-editor scenarios; the page does not say a single machine writing in place produces one.
- **Open / locked files:** "Dropbox stopped syncing" (https://help.dropbox.com/sync/files-not-syncing): "If your file is read-only or is locked by a non-Dropbox application, you can't sync your file to Dropbox."; files open in another app "may not sync properly". File Provider page (https://help.dropbox.com/installs/macos-faqs): files actively edited by an application may not sync; "To resume syncing, close the applications that are actively editing these files."
- **Change-detection mechanism:** **unverified** — no help-centre page describes it; the engineering post "Rewriting the heart of our sync engine" (https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine) describes the Nucleus three-tree model and hashing in a thread pool but not how local changes are observed or what happens if a file changes mid-upload.
- **Write-in-place vs temp+rename:** Dropbox has no documentation distinguishing them (**unverified**). A rename is a new inode replacing the target; the only documented conflicted-copy triggers are multi-editor.
- **Application data / databases / constantly-changing files:** no official help page found; only Dropbox Community staff replies ("We recommend that people do not sync live databases with Dropbox", https://www.dropboxforum.com/discussions/101001014/files-generated-by-microsofts-sql-dont-sync-/663969 — page is JS-rendered, wording **unverified**).
- **Selective sync** (https://help.dropbox.com/sync/selective-sync-overview): removes whole folders from the hard drive, per computer. **Online-only** (https://help.dropbox.com/sync/make-files-online-only): "An online-only file is stored in the cloud and won't take up storage space on your computer"; Preferences → Sync → "Default sync preference" can be set to Online-only for "All future files and folders added directly in the root directory of your Dropbox"; otherwise files are available offline. Admin setting "Save hard drive space automatically" can evict unopened files to online-only (https://help.dropbox.com/sync/admins-online-only-settings).

### D2. Dropbox on macOS with File Provider

- "Expected changes with Dropbox on File Provider" (https://help.dropbox.com/installs/macos-faqs, updated 2025-03-14): uses "Apple's updated File Provider API"; macOS 12.5+; "Your Dropbox folder will be moved to ~/Library/CloudStorage."; moving the folder is not supported; "Sync performance is now regulated by macOS." (throttled on low battery / unplugged / hot); LAN sync unsupported; macOS packages become regular files; files in use may not sync. Files not marked "Make available offline" "may be automatically set to online-only when your hard drive is low on disk space."
- "Dropbox support for macOS on File Provider" (https://help.dropbox.com/installs/dropbox-for-macos-support, updated 2025-11-13): the File Provider migration is opt-in, "this migration isn't required for you to continue using Dropbox"; you can opt out (sign out, sign in, "Opt out" under Advanced), after which "you'll need to re-download any offline files". So the legacy mode still exists as of Nov 2025; no retirement date stated.
- **Online-only by default?** Not by default: the sync overview says available-offline is the default state, and online-only applies only when the Default sync preference is set to Online-only or under disk pressure (above). On macOS, opening an online-only file: "The file will be downloaded within your Dropbox folder and will open in its default app."; "Online-only files on macOS 12.3 and higher will show as zero bytes in size." (https://help.dropbox.com/sync/online-only-mac). Right-click → "Make available offline" pins a folder.
- **Apple's dataless-file semantics:** "Synchronizing the File Provider Extension" (https://developer.apple.com/documentation/fileprovider/synchronizing-the-file-provider-extension): "A dataless copy just stores the information needed to display the item in the UI, while a materialized copy includes the item's content." / "if the user opens a dataless file, the system calls fetchContents(...) and saves the file's content." / the system "won't convert a materialized item into a dataless item if the item has pending changes". TN3150 "Getting ready for dataless files" (https://developer.apple.com/documentation/technotes/tn3150-getting-ready-for-data-less-files): "when a person taps the same file, or an app accesses it, the system redownloads the file's content and makes it available again — a process known as materialization." / "Materializing a dataless file can take time if the file is large or there are poor network conditions. In such a scenario, the app may become unresponsive." / symptoms include "Time-out errors (ETIMEDOUT) when invoking file system APIs"; detect with `SF_DATALESS` in `stat.st_flags`; opt out of auto-materialization with `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, ..., IOPOL_MATERIALIZE_DATALESS_FILES_OFF)` and handle `EDEADLK`. Framework overview: https://developer.apple.com/documentation/fileprovider.
- Implication: DuckStation uses plain `fopen`/`fread` with no dataless handling, so an evicted `.mcd`/`.sav` under `~/Library/CloudStorage/Dropbox` blocks on first access until materialized (or errors on a bad network). Pin the folders "Make available offline".
- Apps that watch/lock files in CloudStorage: no Dropbox help page; community threads report Logic Pro files blocked "while File Provider is in sync" (https://dropboxforum.com/discussions/101001016/issues-with-dropbox-file-provider-on-the-mac/710461) — bodies not fetchable, **unverified**.

### D3. Emulator data in Dropbox: reports, and how DuckStation writes

- **Reports:** `gh search/issues` for dropbox / onedrive / icloud / "google drive" / "conflicted copy" in `stenzek/duckstation` returned 0 issues (2026-10-28; the project keeps a limited tracker, so weak evidence). RetroArch's own Cloud Sync docs (https://docs.libretro.com/guides/retroarch-cloud-sync/): "A conflict occurs when the same file is modified on multiple devices before they have a chance to sync." — advice is not to run on several devices at once and to close content before quitting. Libretro forum (2017, https://forums.libretro.com/t/trying-to-sync-saved-states-between-pc-and-android/): battery saves synced fine via Dropbox, save states crashed the other device; maintainer hunterk: save states can change between versions, SRAM is more portable. No DuckStation+Dropbox threads found on Reddit (only SEO guide sites, ignored). A broader cross-repo GitHub search hung on the API — **not completed**.
- **How DuckStation writes (verified in the clone at d3818375):**
  - `FileSystem::CreateAtomicRenamedFile` / `WriteAtomicRenamedFile` / `CommitAtomicRenamedFile` (https://github.com/stenzek/duckstation/blob/master/src/common/file_system.cpp, ~lines 1349–1400): the temp file is the final path + `.XXXXXX` via `mkstemp` (a sibling in the same directory), written, `fclose`d, then `rename()`d over the target. No `fsync`/`F_FULLFSYNC` in file_system.cpp.
  - `settings.ini`: `INISettingsInterface::Save` (https://github.com/stenzek/duckstation/blob/master/src/util/ini_settings_interface.cpp, ~lines 390–408) builds the whole INI and writes it via Create/Commit under a mutex; load reads the file to a string — nothing is held open.
  - Memory cards: the 128 KiB image is loaded fully at open and never kept open; a game write marks it changed and queues a save `SAVE_DELAY_IN_SECONDS = 5` later (https://github.com/stenzek/duckstation/blob/master/src/core/memory_card.h line 49); `MemoryCardImage::SaveToFile` is `FileSystem::WriteAtomicRenamedFile(...)` (https://github.com/stenzek/duckstation/blob/master/src/core/memory_card_image.cpp line 129) — a full rewrite via temp+rename, never in place.
  - Save states: `System::SaveState` (https://github.com/stenzek/duckstation/blob/master/src/core/system.cpp, ~lines 3318–3375) serialises to memory, optionally renames the old file to `.bak`, then `CreateAtomicRenamedFile` → write → `CommitAtomicRenamedFile`; refused "while memory card is being saved" (line 3328). RAM/SPU dumps also use `WriteAtomicRenamedFile` (lines 4210, 4232).
- **Net assessment:** every DuckStation write to the folders you'd redirect (save states, memory cards, settings.ini) is write-temp-then-rename with the file closed before the rename, so Dropbox never sees a half-written file or DuckStation holding the target open; the documented conflicted-copy triggers (two editors, file left open with auto-save) do not apply to one machine. Transient `*.XXXXXX` siblings will appear briefly in the synced folder (whether Dropbox uploads-then-deletes them is **unverified**). Remaining documented risks: (1) two Macs writing the same card/state before sync completes → conflicted copy; (2) eviction to online-only → blocking materialization on `fopen` (pin the folders); (3) macOS-regulated File Provider throttling on battery/heat delaying upload; (4) Dropbox's own warning that files open in an app may not sync — DuckStation does not hold these files open, but the `settings.ini` written on every settings change and the game-list cache in `DataRoot` would churn if the whole DataRoot were in Dropbox, which is one reason to redirect only `[Folders] SaveStates` and `[MemoryCards] Directory` rather than the data root.

## Summary of the decision-relevant facts

1. **DuckStation gives you no clean data-dir override**: no flag, no env var besides `HOME`; portable mode needs `portable.txt`/`settings.ini` *inside* `DuckStation.app/Contents/MacOS` and then writes all data there (seal-breaking, and "pre-configured settings and packages are considered modifications" under its licence). Redirecting individual folders via `[Folders] SaveStates` / `[MemoryCards] Directory` etc. in `~/Library/Application Support/DuckStation/settings.ini` is the supported route; relative values resolve against DataRoot, absolute values are used as-is, and the UI persists them as `..`-relative.
2. **Licence**: CC BY-NC-ND 4.0 since 2024-09-01. Private use on your own machine is unconstrained (no "Sharing"); redistributing an unmodified zip is allowed non-commercially; the author considers pre-configured packages modifications, and RetroDECK froze DuckStation as a "legacy component" for this reason. A managed download of `duckstation-mac-release.zip` from the `latest`/`preview` GitHub release tags into Ludeum's own folder sidesteps redistribution entirely.
3. **The official macOS build is ad-hoc signed, not notarized, has no Homebrew cask, and self-updates in place** (`[AutoUpdater] CheckAtStartup=false` to stop that). It has no single-instance guard and no file-open handler.
4. **Nesting** is documented only in `Contents/Helpers`/`Contents/MacOS`; the nested app keeps its own signature; sign inside-out, never `--deep`; Launch Services registers nested apps anywhere and DuckStation's document claims would surface in Open With; Qt is indifferent to nesting; quarantine/translocation only matter if the zip was browser-downloaded (use `curl`+`unzip`, or strip the xattr).
5. **Dropbox**: DuckStation's writes are all temp+rename and nothing is held open, so single-machine sync is benign; pin the folders "Make available offline" to avoid dataless-file stalls; conflicted copies only arise from two machines racing.
