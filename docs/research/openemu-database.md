# How OpenEmu 2.4.1 reads, writes and re-syncs its library database

Research for issue #2, which feeds Fog item 2 ("Is writing to OpenEmu safe?") and item 9 (Covers) in [`docs/spec.md`](../spec.md). Vocabulary follows [`CONTEXT.md`](../../CONTEXT.md). Researched 2026-09-26.

The question: from OpenEmu's source at the 2.4.1 tag, what is the Core Data model for games, ROMs, collections and images; how `Z_PRIMARYKEY` and `Z_OPT` are kept; whether OpenEmu caches, rewrites or re-derives any of this so that a Sync's writes could be lost; and how artwork files are named, stored and referenced.

## Answer in brief

1. **Stars live on the game, not the ROM.** `rating` is an `Integer 16` attribute of the `Game` entity, limited to 0–5 (`ZGAME.ZRATING`). `ROM` has no rating. OpenEmu makes a new `Game` for every newly imported ROM, so in practice each OpenEmu game owns one ROM. "Stars written to every ROM of the Game" therefore means "written to the `ZGAME` row of every ROM matched to the Game".
2. **Collections are one table with three kinds.** `Collection`, `SmartCollection` and `CollectionFolder` are sub-entities of the abstract `AbstractCollection`, so they share one table with a `Z_ENT` discriminator. Only regular `Collection`s have games, through a many-to-many join table (`Z_2GAMES(Z_2COLLECTIONS, Z_7GAMES)` in this library). Smart collections store no predicate: the only one that works is "Recently Added", which is matched by name and recreated at launch if no smart collection exists.
3. **Covers are a UUID-named JPEG in `Artwork/` plus one `Image` row.** The file is `<library>/Artwork/<UUID>`, with no extension, JPEG at 0.9 quality. `ZIMAGE.ZRELATIVEPATH` holds the bare file name. The row also holds pixel width and height, `format = 3` (JPEG) and an optional `source` URL, and it links one-to-one with `Game.boxImage`.
4. **OpenEmu doesn't re-derive stars, collections or covers on launch or re-import.** Nothing in 2.4.1 recomputes ratings or collection membership. Re-importing a ROM that's already in the library is refused by MD5, and no folder watching or re-scan exists. The one automatic rewrite is the **OpenVGDB info sync**. It runs 2 s after every launch, picks up every game whose `status` is 3 ("processing"), and **replaces and deletes its box image** if OpenVGDB has cover art. There is no iCloud, CloudKit or persistent-history code.
5. **Core Data owns `Z_PRIMARYKEY` and `Z_OPT`; OpenEmu never touches them.** The rules come from Core Data itself (closed source), so the spike has to confirm them on a copy. An external writer has to bump `Z_PRIMARYKEY.Z_MAX` past every `Z_PK` it inserts, or Core Data's next insert will collide and the save will fail. OpenEmu saves almost everywhere with `try?`, so that failure would be **silent**.
6. **The store runs in SQLite WAL mode, and on this Mac it lives in Dropbox.** OpenEmu sets no journal-mode pragma, so Core Data's default (WAL) applies. OpenEmu's own UI warns that cloud-synced folders can corrupt the library. That makes backup, write and checkpoint discipline part of Sync safety.

### How that lands in SQLite (CD, PR; confirm in the spike)

Core Data gives each root entity one table, `Z<ENTITY>`, and each attribute a `Z<ATTRIBUTE>` column. Every table has `Z_PK` (the integer primary key), `Z_ENT` (the entity number) and `Z_OPT` (the optimistic-locking version). A to-one relationship becomes a foreign-key column holding the target's `Z_PK`. The one-to-one `Game.boxImage` ↔ `Image.Box` is expected to have a column on **both** sides (`ZGAME.ZBOXIMAGE` and `ZIMAGE.ZBOX`). A many-to-many becomes a join table with no `Z_OPT`. The tables Sync touches:

| Table | Holds | Key columns for Sync |
|---|---|---|
| `ZGAME` | Game | `ZRATING`, `ZBOXIMAGE`, `ZSTATUS` |
| `ZROM` | ROM | `ZGAME` |
| `ZABSTRACTCOLLECTION` | Collection, SmartCollection and CollectionFolder together | `Z_ENT` (which kind), `ZNAME`, `ZFOLDER` |
| `Z_2GAMES` | Collection ↔ Game | `Z_2COLLECTIONS` (collection `Z_PK`), `Z_7GAMES` (game `Z_PK`). PR's query `LEFT JOIN Z_2GAMES c ON c.Z_7GAMES = g.Z_PK` ran against this library. |
| `ZIMAGE` | Image | `ZRELATIVEPATH`, `ZFORMAT`, `ZWIDTH`, `ZHEIGHT`, `ZSOURCE`, `ZBOX` |
| `Z_PRIMARYKEY` | One row per entity: `Z_ENT`, `Z_NAME`, `Z_SUPER`, `Z_MAX` | |
| `Z_METADATA` | Store UUID, model version hashes, and OpenEmu's `romsFolderURL` ([LD L469-L493](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L469-L493)) | **Never write** |

The join-table name implies entity numbers 2 = `Collection` and 7 = `Game`. That fits Core Data numbering entities alphabetically with each sub-entity right after its parent: 1 AbstractCollection, 2 Collection, 3 CollectionFolder, 4 SmartCollection, 5 Contributor, 6 Credit, 7 Game, 8 Genre, 9 Image, 10 ROM, … **Sync should read these numbers from `Z_PRIMARYKEY` (`Z_NAME` → `Z_ENT`) at run time, not hard-code them.**

## 2. `Z_PRIMARYKEY` and `Z_OPT`

**OpenEmu never reads or writes them.** Its code only goes through Core Data object APIs. Its only direct store access is `NSPersistentStoreCoordinator.setMetadata` for the ROMs folder ([LD L488-L489](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L488-L489)). So everything below is Core Data's own behaviour (**CD**, unverified):

- **`Z_PRIMARYKEY.Z_MAX`** is the highest `Z_PK` handed out for an entity hierarchy. On save, Core Data assigns new objects `Z_MAX + 1 …` and raises `Z_MAX`. It doesn't look at `MAX(Z_PK)` in the table.
  - *External insert without bumping `Z_MAX`*: Core Data's next insert of that entity reuses the same `Z_PK`. SQLite rejects it (`UNIQUE constraint failed`) and the save fails. Nothing is corrupted, but OpenEmu's own changes (a new import, a new collection, a new cover) are lost. See the silent-failure risk below.
  - *`Z_MAX` above the real maximum*: harmless gaps.
  - *Which row to bump for inherited entities*: `Collection` rows live in `ZABSTRACTCOLLECTION`, and their keys should come from the **root entity's** row (`AbstractCollection`). **Confirm in the spike**: create a collection in OpenEmu on a copy and see which `Z_PRIMARYKEY` row changes.
- **`Z_OPT`** is a per-row version number. Core Data raises it on every update of that row and uses it for optimistic locking. When a context saves an object it fetched earlier, Core Data checks the row's current `Z_OPT` against the snapshot. A mismatch is a merge conflict, which the context's merge policy resolves. When OpenEmu is closed there are no snapshots, so an external writer can't cause a conflict. The safe convention is still to insert rows with `Z_OPT = 1` and add 1 on every row Sync updates, including both ends of a collection-membership change.
- **When OpenEmu is running**, its contexts use `NSMergeByPropertyObjectTrumpMergePolicy` ([LD L207](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L207), inherited by child contexts at [L250](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L250) and [L260](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L260)). On a `Z_OPT` conflict, OpenEmu's in-memory value wins for each property it changed. The writer context also keeps every object it has loaded (`retainsRegisteredObjects = true`, [L208](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L208)), and at quit OpenEmu saves the writer context ([L116-L125](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L116-L125)). So a Sync while OpenEmu is open would have its star changes overwritten by any game OpenEmu later edits, and OpenEmu would never show the new rows. **This is why Sync must refuse to run while OpenEmu (bundle id `org.openemu.OpenEmu`) is running.** OpenEmu has no way to notice that the store changed on disk: `OELibraryDatabase` observes only app termination and its own context saves ([L105-L107](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L105-L107)), and it uses no persistent-history tracking.

**Saves fail silently.** OpenEmu nearly always saves with `try?`: the writer save after a UI save ([LD L131-L134](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L131-L134)), rating edits ([G L464](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBGame.swift#L464)), the import pipeline ([IO L444-L450](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/ImportOperation.swift#L444-L450)) and the OpenVGDB sync ([LD L713](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L713)). Only the save at quit shows an error ([L119-L124](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L119-L124)). Any external write that makes a save fail therefore loses data *without telling anyone*. That includes a primary-key collision, a `rating` above 5 (the model's maximum, checked when Core Data validates the object), a required `status` left NULL, or a dangling foreign key.

They are a reason to always write a matching row *and* file together. |
| **Cloud** | No iCloud, CloudKit, ubiquity-container or `NSPersistentHistory` code anywhere in the repo. The only mention of iCloud is a warning shown when you move the library: *"a database file which could get corrupted if the library is moved to … Folders managed by cloud synchronization software (like iCloud Drive)"* ([`en.lproj/Localizable.strings` L588](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/en.lproj/Localizable.strings#L588)). | See [section 5](#5-store-location-wal-and-dropbox). |

In short, OpenEmu has no background process that would re-derive stars or collections, so a Sync made while OpenEmu is closed survives the next launch. The exceptions are the OpenVGDB cover replacement for `status = 3` games and the silent save failures above.

## 4. Artwork

- **Folder**: `<library folder>/Artwork/`, created on demand ([LD L566-L572](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L566-L572)).
- **File name**: `UUID().uuidString`, i.e. 36 upper-case hex characters with hyphens and **no extension** ([I L71](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L71), [L106](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L106)).
- **Encoding**: the largest bitmap representation, saved as JPEG at compression factor 0.9 and written atomically ([I L30-L33](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L30-L33), [L77-L114](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L77-L114)).
- **Row** ([I L116-L119](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L116-L119), [L129-L140](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L129-L140)):
  - `relativePath` = the bare file name. It is resolved as `coverFolderURL.appendingPathComponent(relativePath)` ([I L237-L243](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L237-L243)).
  - `width` and `height` = pixel size of that representation.
  - `format` = `NSBitmapImageRep.FileType.jpeg.rawValue`. That's **3** (tiff 0, bmp 1, gif 2, jpeg 3, png 4, jpeg2000 5; worth checking against a real row in the spike).
  - `source` = the URL the image came from, standardised and absolute ([I L253-L255](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L253-L255)), or nil.
  - `Box` ↔ `Game.boxImage`.
- **How it's shown**: the cover grid uses `relativePath` as the image's cache key and shows a placeholder when the file is missing or `relativePath` is nil ([G L500-L522](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBGame.swift#L500-L522)). So Sync should **always write a new UUID file** rather than overwrite an existing one, or a cached image could stay on screen. "No box art in OpenEmu" should mean `ZBOXIMAGE IS NULL`, or an `Image` whose file is missing.
- **Replacing and deleting**: setting a new cover deletes the old `Image` ([G L352-L379](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBGame.swift#L352-L379)). An `Image` removes its file when it's deleted in the root (writer) context ([I L218-L223](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBImage.swift#L218-L223)). Deleting a Game cascades to its box image ([M L31](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDatabase.xcdatamodeld/OEDatabase%201.3.xcdatamodel/contents#L31)). An external writer that deletes an `Image` row has to delete the file itself.
- **`source` matters**: a non-nil `source` lets the Debug actions delete the file and later download it again from that URL. With both `source` and `relativePath` nil, the row counts as "useless". Sync can leave `source` NULL (its Covers are journal-owned) or set it to the IGDB image URL. Either works; NULL keeps OpenEmu from ever dropping the file.

## 5. Store location, WAL and Dropbox

- **Location**: the library folder is the `databasePath` user default (with `~` expanded), and the store is `Library.storedata` inside it ([AD L180-L203](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/AppDelegate.swift#L180-L203), [LD L53-L54](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L53-L54), [L444-L448](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L444-L448)). No symlinks are resolved on this path. The ROMs folder is kept in the store's metadata, relative to the library when it is inside it ([LD L450-L493](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L450-L493)). On this Mac `defaults read org.openemu.OpenEmu databasePath` gives `~/Dropbox/games/OpenEmu/Game Library`, and `~/Library/Application Support/OpenEmu` (save states, cores, `openvgdb.sqlite`) is a symlink into Dropbox as well. Sync should find the store the same way OpenEmu does, from `databasePath`, not from a hard-coded path.
- **Journal mode**: OpenEmu passes only the two migration options when it opens the store, and no `NSSQLitePragmasOption` ([LD L190-L196](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L190-L196)). So Core Data's default applies, which is **WAL** since OS X 10.9 (QA1809). Recent writes can sit in `Library.storedata-wal` until a checkpoint. QA1809 warns that copying only the main file loses data. The store is really three files: `.storedata`, `-wal` and `-shm`.
- **Risks under a file-syncing folder**:
  1. **Backups**: a Sync backup has to include all three files, taken while OpenEmu is closed, or use SQLite's online backup API or `VACUUM INTO`. Copying only `Library.storedata` can produce an old or inconsistent database.
  2. **Dropbox uploads files independently.** While Sync is writing, Dropbox can upload the main file and the WAL at different moments, and another device (or a Dropbox restore) can bring back a mismatched pair. Sync should write in one transaction, then run `PRAGMA wal_checkpoint(TRUNCATE)`, so the finished state is all in `Library.storedata` with an empty WAL before Dropbox picks it up.
  3. **Conflicted copies**: if another Mac with OpenEmu uses the same Dropbox library, or Dropbox holds an older version, Dropbox can make "conflicted copy" files or replace the store underneath OpenEmu. OpenEmu's own warning says such folders can corrupt the library. This risk exists without Sync, but Sync adds writes, so Sync should check it's the only writer. Running `PRAGMA integrity_check` before and after is cheap.
  4. **Artwork**: new Cover files in `Artwork/` sync separately from the database. Another device could briefly see a row whose file isn't there yet, which OpenEmu shows as a placeholder. That's harmless.

## 6. Corrections to the spec and ticket

- *"Stars on ROMs"* (ticket) and *"written to every ROM of the Game"* (spec, Sync to OpenEmu) are wrong: the stars are on the game. Sync writes `ZGAME.ZRATING` for each OpenEmu game that owns a ROM matched to the journal Game. Since each OpenEmu game has one ROM, "every ROM" in practice means "every OpenEmu game that has one of this Game's ROMs". Write 0, not NULL, for "no stars" (the model default is 0), and never write a value above 5.
- *"Smart collections are left alone"* is easy to honour. Sync should delete only rows whose `Z_ENT` is `Collection`, never `SmartCollection` or `CollectionFolder`. Deleting a folder cascades to its sub-collections.
- Deleting a collection by SQL has to delete its `Z_2GAMES` rows too. That's what the nullify rule does inside Core Data.
- Journal-owned collections (`_TODO`, the Lists and so on) are best **updated in place**, keeping their `Z_PK`, instead of being deleted and recreated. That keeps OpenEmu's sidebar selection, which is saved as the object's `x-coredata://<store UUID>/Collection/p<Z_PK>` URI ([C L49](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBCollection.swift#L49), [OEDBItem L68-L81](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OEDBItem.swift#L68-L81)), and it creates fewer primary keys.
- A side note for Import: the OpenVGDB sync has a typo that can write a serial into `ROM.md5` (`rom.md5 = serial`, [LD L703-L706](https://github.com/OpenEmu/OpenEmu/blob/v2.4.1/OpenEmu/OELibraryDatabase.swift#L703-L706)). It only fires when the ROM has no serial and the looked-up info contains one, which the key-merge order seems to prevent. Still, Import shouldn't assume every `ZMD5` is a 32-character hex string.

## What the spike must still check

All of these on a **copy** of the library (all three store files plus `Artwork/`), never on the live Dropbox one:

1. **Real schema**: dump `sqlite_master` and `Z_PRIMARYKEY`. Confirm the table and column names above, the `Z_ENT` numbers, the one-to-one columns `ZGAME.ZBOXIMAGE` and `ZIMAGE.ZBOX`, the `ZFORMAT` value on an existing JPEG row, and that `PRAGMA journal_mode` is `wal`.
2. **Which `Z_PRIMARYKEY` row gets bumped**: create one collection in OpenEmu on the copy and diff `Z_PRIMARYKEY` and `ZABSTRACTCOLLECTION` (is it the `AbstractCollection` row or the `Collection` row?). Do the same for a cover (`Image`).
3. **Collision test**: insert a collection row *without* bumping `Z_MAX`, launch OpenEmu and create a collection. Expect the save to fail quietly and the new collection to be gone after a relaunch. Then repeat *with* the bump and expect success. This shows whether the bump is necessary and enough.
4. **Round trip**: Sync stars (0–5), collections (create, rename, change membership, delete), and a Cover (new UUID JPEG and `ZIMAGE` row, both foreign keys set). Launch OpenEmu, change something in the UI, quit, and relaunch. Check that nothing reverted and that `PRAGMA integrity_check` passes.
5. **OpenVGDB interaction**: give a Cover to a game with `ZSTATUS = 3`, then launch. Confirm it gets replaced, and decide whether Sync should skip such games or wait for their status to go back to 0.
6. **Validation**: write `ZRATING = 6` on a copy and confirm OpenEmu's next save of that game fails. This shows why values have to be clamped to 0–5.
7. **WAL and checkpoint**: after Sync, `PRAGMA wal_checkpoint(TRUNCATE)` leaves an empty `-wal`, and OpenEmu opens the result cleanly.
8. **Running-app guard**: Sync refuses to run while `org.openemu.OpenEmu` is running.
