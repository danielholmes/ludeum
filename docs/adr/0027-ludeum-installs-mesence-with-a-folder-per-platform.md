# Ludeum installs MesenCE, with a folder per Platform for what it keeps

Amends [0024](0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md) (Open leaves the Emulators sheet, for every Emulator), [0008](0008-journal-owns-per-game-emulator-settings.md) (a Play no longer lands in a running MesenCE, and MesenCE's own settings now last) and [0012](0012-rename-writes-no-intro-names.md) (Rename of a MesenCE ROM renames the file inside its `.7z` and its saves).

I want MesenCE's Save states and Game saves in the Data folder so Dropbox has them, as DuckStation's are (0024), and the MesenCE Ludeum plays with to be Ludeum's own. The research is [mesence-under-ludeums-management.md](../research/mesence-under-ludeums-management.md). Most of 0024's model fits: MesenCE's releases are versioned tags with a SHA-256 in GitHub's API, a `settings.json` beside its executable makes it portable, and its Save state, Game save and screenshot folders are each an absolute path in that file. Four things differ.

- **It plays eleven Platforms, and keys everything by the ROM's file name alone.** A Save state is `<name>_<slot>.mss` and a Game save `<name>.<ext>`, where the name is the ROM file's without its extension (the file inside a `.7z`'s), with nothing of the console in it, in one folder for every Platform. Thirteen names in my ROM folders are on two or three of MesenCE's Platforms (`DuckTales (USA)` on Game Boy and NES), and saving slot 1 in one overwrote the other's slot 1 when I tried it. So each Platform gets its own folders, which a Play can only set by writing `settings.json` before MesenCE starts: it reads the file once, and a folder can't be set on its command line.
- **A Play can't start it from a Save state in one go.** A state named on the command line loses a race with the ROM loading on another thread. What works, every time in a spike of 22 cold launches, is MesenCE's own resume file: `RecentGames/<name>.rgd`, a zip of the state and the ROM's path, which `--loadLastSession` loads after the ROM, synchronously.
- **Every build says it's 2.2.1**, and there's no version flag, so the build can't be asked for.
- **The 2.2.1 release needs Homebrew's SDL2**, linked by absolute path. Builds since don't, but there's no release of them yet.

So:

- **Ludeum installs MesenCE**, as it does DuckStation: Install in the Emulators sheet, a Background task, fetches `Mesen_2.2.1_macOS_ARM64_AppleSilicon.zip` from `nesdev-org/MesenCE`, checks it against the SHA-256 pinned in code, unpacks it (a zip inside a zip) without quarantine, writes `settings.json` into `Contents/MacOS` to make it portable, names it `Emulators/MesenCE.app` in the Ludeum folder and records the digest it installed there. The version check compares that record with the pin, since MesenCE can't say. The first `settings.json` is a copy of the one MesenCE already has in `~/Library/Application Support/MesenCE`, controls mapped, else a minimal one that has MesenCE fill in its default controls. A reinstall carries across what the old copy kept in its data root but the native code MesenCE unpacks there on every launch. Install and Play are refused while Homebrew's SDL2 is missing, saying how to get it. `/Applications/Mesen.app` is no longer looked up.
- **A folder per Platform.** Every Play's **Standing settings** point MesenCE's Save state, Game save and screenshot folders at `Data/Emulators/MesenCE/<Platform>/Save States`, `Saves` and `Screenshots`, the Platform named as its ROM folder is, so Famicom's are apart from NES's. They also turn the update check off, turn the game selection screen off (so MesenCE writes no resume files of its own, which no setting can move and which would clash across Platforms), and turn MesenCE's automatic Save state on, every minute: with no resume file written on quitting, that's what a Game resumes from.
- **Play is refused while any MesenCE is running**, Ludeum's or another: it would ignore the folders written for this Play, and every launch opens a separate MesenCE anyway, as its single-instance hand-off doesn't work in the macOS build. Run-ahead and Game Boy model stay on the command line (0008), but `--doNotSaveSettings` goes, so a control or video setting changed in MesenCE lasts; the Standing ones are written again at the next Play.
- **Play from a Save state** writes `RecentGames/<name>.rgd` in MesenCE's data root, holding the chosen state and the ROM's path as MesenCE writes them, then opens the ROM with `--loadLastSession`. With the game selection screen off, MesenCE never writes that file itself.
- **Game detail** lists a MesenCE Game's Save states, slots 1 to 10 and the automatic one as Resume, each with its screenshot, decoded from the picture MesenCE stores in the state as each console draws it, to Play from or delete; and its Game saves, the files MesenCE keeps for it, with when each was last written. There's no backup, restore or delete of a Game save, as for DuckStation: Dropbox keeps earlier versions.
- **Rename follows the name MesenCE keys by.** Renaming a MesenCE ROM renames the file inside its `.7z` too (7-Zip's `rn`, without repacking), and moves its Save states and Game saves in its Platform's folders to the new name. It's refused when a save under the new name is already there. A disc ROM's cue sheet keeps its name, as before, and so do its saves.
- **Firmware stays inside the app**, not in the Data folder: MesenCE has no setting for it, and it's set up again if it's lost. A reinstall carries it across.
- **Open leaves the Emulators sheet**, for every Emulator. An Emulator's own settings are changed during a Play, which writes the Standing settings first anyway.
- **One Mac writes the Data folder at a time**, as 0024 says. MesenCE writes its states, saves and settings in place rather than under a temporary name, so a crash mid-write can leave half a file; the MesenCE folders are marked available offline in Dropbox, as DuckStation's are.

## Considered Options

- **One folder for every Platform**, as MesenCE has it: rejected for the thirteen clashing names. It would have kept a running MesenCE taking a Play, had its hand-off worked.
- **Pin a nightly that doesn't need SDL2**: rejected. A nightly is a GitHub Actions artifact that expires, so it can't be "a tag and a digest in code"; the next release will do, and is a bump.
- **Patch 2.2.1 to load an SDL2 Ludeum supplies** (`install_name_tool`, then re-signing): rejected, as surgery on someone else's binary for one release.
- **Firmware in the Data folder through a link**: rejected. It can be set up again.
- **Keep MesenCE's resume files** and move the state out after each Play: rejected. It's the copying around a launch that 0024 did away with, and they can't be moved.
- **Play from a state some other way**: a state after the ROM on the command line loses the race (1 of 13 launches); a second launch with the state opens a second MesenCE; a Lua script works but opens a script window and needs an address range per console.
- **Ludeum names inside archives by hand, leaving Rename alone**: rejected; a renamed loose ROM would orphan its saves.

## Consequences

- Moving over is by hand, once, with MesenCE closed: Install first, then `ludeum-import mesence` (a plan unless `--run`) moves each file in `~/Library/Application Support/MesenCE/SaveStates`, `Saves` and `Screenshots` into the Platform folder of the one ROM its name matches, listing any it can't place, copies its `Firmware` into the installed copy, and renames the file inside each MesenCE `.7z` whose name differs from the archive's, moving its saves with it. It goes once it's run. Deleting `/Applications/Mesen.app` and the old folder is mine to do.
- OpenEmu's Game saves for MesenCE's Platforms come across by hand afterwards, matched to their ROMs, renamed to MesenCE's names in each Platform's `Saves` (#76), but for six GBA EEPROM saves, whose 8-byte blocks MesenCE stores the other way round.
- A new Mac downloads MesenCE once, from the Emulators sheet, after `brew install sdl2`.
- An Emulator's settings can only be reached during a Play now, DuckStation's included.
- Quitting without saving a state loses up to a minute of play, since the last automatic Save state; a Game save is written by MesenCE only when the Game stops, so a crash loses that session's.
- The clash stays wherever two of a Platform's ROMs share a name inside their archives, which a ROM folder can't hold for loose files.
