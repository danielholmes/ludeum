# Ludeum installs DuckStation, portable, and says where it keeps things

Amended by [0029](0029-a-playstation-games-own-settings-are-duckstations.md): a Play no longer writes the per-game file, so what every Play wrote into it before this is no longer taken out as a Play meets it, and a Game needs a Serial only for its Save states and memory card.

Amended by [0027](0027-ludeum-installs-mesence-with-a-folder-per-platform.md): Open leaves the Emulators sheet, so the Standing settings are written before every Play and after Install, and DuckStation's own settings are reached during a Play.

Supersedes [0022](0022-duckstation-save-states-stay-its-own-and-are-backed-up.md) and [0023](0023-a-playstation-games-memory-card-lives-in-the-data-folder.md), and amends [0010](0010-a-fixed-data-folder-linked-into-dropbox.md) (the Ludeum folder now holds an Emulator) and [0021](0021-duckstation-settings-go-in-its-per-game-file-named-by-the-discs-serial.md) (fast boot, frame pacing and the memory card keys leave the per-game file).

I want DuckStation's save states and memory cards in the Data folder so Dropbox has them, with none of the copying 0022 needed, and I want the DuckStation that Ludeum plays with to be Ludeum's own: not a copy I install and update by hand, exposed to the OS as any app, and not one whose settings Ludeum has to stay compatible with. In practice I only ever open it through Ludeum.

Two findings decided the shape. First, the Dropbox goal never needed a different binary: every folder DuckStation keeps is a key in its `settings.ini` (`[Folders] SaveStates`, `[MemoryCards] Directory`, `[BIOS] SearchDirectory` and the rest) that takes an absolute path, and what stopped Ludeum writing them was only 0022's own rule that DuckStation's settings stay clear of Ludeum. Second, DuckStation offers no command-line argument or environment variable for its data folder (only `HOME`, read literally); its portable mode is a `portable.txt` inside the bundle at `Contents/MacOS/`, which makes that folder the data root.

So:

- **Ludeum installs DuckStation.** Install is a button in the Emulators sheet, a Background task: fetch `duckstation-mac-release.zip` for the pinned versioned tag (`v0.1-12083` to begin with) from the main repo, else from `duckstation/old-releases` once it has aged off the first thirty, check it against the SHA-256 pinned beside the tag in code (GitHub's release API gives one per asset), unpack without quarantine, confirm the build with `-version`, write `portable.txt`, and swap it into `Emulators/DuckStation.app` in the Ludeum folder. DuckStation is no longer looked up by bundle ID; any other install is ignored. A bump is the tag and digest in code. Rolling tags (`latest`, `preview`) can't be pinned: their zip is replaced on every build, and the build Ludeum was written against, 12442, only ever existed under one.
- **It's portable**, so its data root is inside its own bundle and shares nothing with another DuckStation. The **Standing settings** point every folder worth keeping into `Data/Emulators/DuckStation/` (`Save States`, `Memory Cards`, `BIOS`, `Game Settings`, `Input Profiles`, `Screenshots`), turn the auto-update check off, and carry fast boot and lowest input latency, which no longer need a per-game file to be global. What has no key stays in the bundle: `settings.ini`, play time, any custom properties, crash dumps and the rebuildable caches. A reinstall carries all of that across into the new bundle, the caches included (cheaper than telling them apart), and keeps the old copy beside it until it's across. The writes break the bundle's resource seal, which doesn't matter for an ad-hoc-signed app that was never quarantined. `settings.ini` can't be linked out of the bundle, as DuckStation renames a fresh file over it on every save.
- **Standing settings are written before every launch Ludeum gives DuckStation**, Play and Open alike, and after Install, so a setting changed in DuckStation's own UI lasts only until then, as 0021 already accepts per game. Everything else in `settings.ini` is DuckStation's, set in its UI, which Ludeum's Open button reaches.
- **Only while DuckStation isn't running.** It keeps settings in memory and rewrites the whole file on any change, and it has no single-instance guard, so Play is refused while any DuckStation is running, as it is while the managed copy is missing or not the pinned build, each with its reason and a pointer to the Emulators sheet.
- **Save states live in the Data folder, full stop.** The backup, the folder watcher, Restore and "not in DuckStation" go. Listing, Play from a state and Delete work on the files there.
- **DuckStation names and manages memory cards; Ludeum only says where.** The per-game file no longer carries `Card1Type` or `Card1Path`, and nothing is copied in at first Play. What every Play wrote into a per-game file before this (the Standing keys, and card 1 as the Serial-named card) is taken out as a Play meets it, as the Game's settings always were ("one it hasn't is taken out"): that's the Play writing the file it owns, not a migration, and a value set since in Game Properties stays. Game detail shows a Game's card and its Card saves by working out DuckStation's name for it from its settings and game database, which it already did for cards not yet copied. A Game whose Disc 1 has no Serial can be Played again (it still needs one for its own settings and its save states). Cards are no longer per ROM by Serial: a card follows DuckStation's naming, by default the disc's title in its database, shared across a disc set.
- **One Mac writes the Data folder at a time.** DuckStation writes states, cards and settings under a temporary name and renames them into place, so Dropbox never sees half a file, and the only documented way to a conflicted copy is two machines racing. The DuckStation folders in the Data folder are marked available offline in Dropbox, as DuckStation reads with plain file calls and would stall on an evicted file.

## Considered Options

- **DuckStation.app nested inside Ludeum.app** (`Contents/Helpers`): rejected. Its self-updater rewrites its own bundle, breaking Ludeum's seal; its licence (CC BY-NC-ND 4.0 since September 2024) treats "pre-configured settings and packages" as modifications, so a configured copy inside a Ludeum build could never be shared; it'd still be registered by Launch Services and appear in Open With; and every DuckStation update would be a Ludeum rebuild pulling a 96 MB zip. No macOS launcher ships a third-party emulator in its bundle; OpenEmu, the local precedent, downloads cores into Application Support, which is what this does.
- **The binary stays in /Applications and Ludeum writes its global settings**: rejected, though it alone would have met the Dropbox goal. It leaves DuckStation a separate app to the OS and to me, and a hand update can break Play, as build 8843 did when it dropped `-settings`.
- **A link at `~/Library/Application Support/DuckStation` into the Ludeum folder** as the data root: rejected. DuckStation resolves it, and it's the same trick as 0010, but any other DuckStation install would share it.
- **A changed `HOME` on launch**: rejected. It isolates completely, Qt's and Cocoa's own files included, and writes nothing into the bundle, but it holds only for launches from Ludeum (a double-clicked copy would run blank and separate) and leans on a side effect of DuckStation's path code rather than a feature.
- **Ludeum keeps naming cards by Serial** (0023) with a Standing setting for the directory on top: rejected. Game saves are DuckStation's concern; Ludeum shows them.
- **An automatic migration at first launch**: rejected. One-off moves of files are done by hand, by a script with a dry run that's deleted once used, so the app carries no code that runs once.

## Consequences

- Moving over is by hand, once, with DuckStation closed: Install first, then `scripts/migrate-duckstation.sh` moves `savestates` into the Data folder's `Save States` (keeping the newer of any name both have, the older set aside), `memcards`, `bios`, `gamesettings`, `inputprofiles` and `screenshots` to their Data folder names, and the rest of the old root (`settings.ini` with its controller and video settings, play time, caches) into the installed copy's data root; then `ludeum-import duckstation-cards` gives the Serial-named cards DuckStation's names (the older of two set aside, never deleted) and takes the card keys out of the per-game files. Deleting `/Applications/DuckStation.app` and the old folder is mine to do. Both go once they've run.
- A new Mac downloads DuckStation once, from the Emulators sheet, before any PlayStation Play.
- The pin lags the rolling release by a week or two, as versioned tags do.
- DuckStation's memory card editor now lists every card, since they're all in its directory.
- A card DuckStation named lands in the Data folder as soon as a game writes it, so cards brought across from OpenEmu (#76) go in under DuckStation's names.
- The other Emulators stay as they are, found by bundle ID and installed by hand, each with its own issue (#82 to #89) for when it gets the same treatment, which may need its own model.
- DuckStation's `Emulator` version check becomes an exact build; the others keep their minimum.
