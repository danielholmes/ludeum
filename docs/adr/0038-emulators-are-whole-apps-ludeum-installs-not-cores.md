# An Emulator is a whole app Ludeum installs and configures, not a core it runs

Names the model [0024](0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md), [0027](0027-ludeum-installs-mesence-with-a-folder-per-platform.md), [0028](0028-ludeum-installs-ares-and-says-where-it-keeps-things.md), [0032](0032-ludeum-installs-pcsx2-and-says-where-it-keeps-things.md), [0035](0035-an-amiga-rom-is-one-archive-and-its-saves-are-amiberrys-save-images.md) and [0036](0036-ludeum-installs-ymir-and-gives-each-game-its-own-backup-ram.md) each chose for one Emulator, so the four still to bring across (#83 Dolphin, #85 melonDS, #87 PPSSPP, #89 xemu) and any Emulator after them follow it without reopening the question.

Ludeum has played its Games three ways. First, each Emulator was an app installed on the Mac like any other, found by its bundle ID and handed a ROM: cheap, but a hand update could break Play (DuckStation build 8843 dropped `-settings`), and Ludeum could show nothing of what the Emulator kept. Since 0024, an Emulator is a pinned release Ludeum fetches, checks and keeps in the Ludeum folder apart from any other copy, with its Standing settings written before each Play so its Save states and Game saves land in the Data folder, and its own UI for everything else. OpenEmu, which the journal replaced, did a third thing: each emulator was a core, a plugin that ran one frame at a time inside OpenEmu, which owned the frame loop, the input mapping, the Save state files and their UI for every system alike. The question, with six of ten Emulators managed, was whether to finish that way or move to cores. The research is [emulator-integration-models.md](../research/emulator-integration-models.md).

Two findings decided it. First, the cores aren't there: of Ludeum's ten Emulators, only Dolphin, melonDS and PPSSPP exist as a core in OpenEmu or libretro, and Dolphin's is a fork. DuckStation's licence forbids a repackaged copy and its author withdrew its core; PCSX2, ares, MesenCE, Ymir, xemu and Amiberry have none. A core-based Ludeum would be Mednafen for PlayStation and Saturn, PUAE for Amiga and nothing for PlayStation 2 or Xbox, which is OpenEmu's roster, and OpenEmu's last release was December 2023, Intel-only. Second, a core's contract is a ceiling: OpenEmu's core API gives a core a few option flags and a Display Modes menu, libretro's a list of options the port chose to expose, and neither reaches the emulator's own settings. The managed model has the opposite shape: Ludeum fixes only what it needs (where things go, latency, a state to start from) and 0033 could hand "how DuckStation plays" back to DuckStation setting by setting. The unification I liked in OpenEmu, one list of Save states and one Resume for every Game, Ludeum draws from the Emulators' own files, as the Save state entry and 0034 already do.

So:

- **An Emulator is a whole app**, its author's release, that Ludeum installs at a pinned version, keeps apart from any other copy, and launches with its Standing settings written and its Emulator settings on the command line or in its files. Nothing of an emulator runs inside Ludeum: no frame loop, no audio or video, no input mapping.
- **Ludeum owns where things go, not how the game plays.** Its Standing settings are paths, self-updating off and what each ADR names as Ludeum's (latency, auto-save); the rest is set in the Emulator, during a Play, and lasts.
- **What Ludeum shows of a Game's play, it reads from the Emulator's files**: Save states, a Resume state, Game saves, each in the Emulator's own format and naming, listed, Played from and deleted as the Emulator allows. Where an Emulator can't do a thing (ares's states have no screenshot, Dolphin's states have no folder setting), Ludeum shows less rather than reaching into the emulator.
- **Each Emulator still gets its own research note and ADR**, because each keeps its files differently; this decision fixes only the model they work within.

## Considered Options

- **OpenEmu's model, cores inside Ludeum**: rejected. Seven of ten Emulators have no core, and the three that do would need a frame loop, audio, video and input stack in Ludeum and a wrapper per emulator for Ludeum to maintain, as OpenEmu maintained 25 forks. The settings ceiling is the thing I most dislike in OpenEmu, and it's structural.
- **libretro cores hosted by Ludeum, or RetroArch launched as an Emulator**: rejected for the same roster reason. RetroArch as a managed Emulator would be one more app with its own settings file, playing lesser emulators for the Platforms that matter most.
- **A hybrid, cores for the 8-bit and 16-bit Platforms and whole apps for the rest**: rejected. What a core would add there (one Save state format with screenshots, rewind, run-ahead) MesenCE already has natively, and the hybrid would put the whole emulation stack into Ludeum for the Platforms that need it least.
- **Back to the launcher model, Emulators installed by hand**: rejected. It's what 0024 left, for a hand update breaking Play and Ludeum seeing nothing of what an Emulator kept.

## Consequences

- #83, #85, #87 and #89 go ahead as managed Emulators, each with its own ADR, without weighing the model again. PPSSPP waits for a release with its flags, as its note says.
- An Emulator that can't be managed well (no setting for its Save states, no flag for a state to start from) is managed as far as it allows, and the gap is recorded in its ADR, not worked around by running it inside Ludeum.
- A Platform with no standalone emulator worth managing has no Emulator. A libretro-only emulator would mean this decision is reopened, not a core host added quietly.
- Rewind, run-ahead and shaders stay each Emulator's own, so a Platform has them only where its Emulator does.
