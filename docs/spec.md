# Ludeum: spec

A native macOS app for keeping a personal journal of the games I play on every Platform: ratings, Playthroughs, what to play next. It reads my ROMs from a folder per Platform and opens them in each Platform's Emulator.

This file holds the decisions made so far and the open questions (fog). Vocabulary is defined in [`GLOSSARY.md`](../GLOSSARY.md). The reasons behind hard-to-reverse choices are in [`docs/adr/`](adr/). Where this file and those disagree, the glossary and the ADRs win, and this file needs fixing.

## Goals

- Journal data belongs to a **Game**, and to its **Copies**: a ROM is a Copy and carries its own Copy details ([ADR 0011](adr/0011-roms-are-copies.md)). Removing or re-adding a ROM's file, or swapping it for another Version, loses nothing; only deleting a ROM from the journal does.
- Richer data than an emulator's library offers: a Rating out of 10 in steps of 0.1 with its history, notes, and Playthroughs with Partial dates.
- Covers every Platform (retro, PC, Xbox, …), not just emulated games.

## Non-goals (for now)

Phone or remote access; several Macs; importing from Steam or Xbox; exceptions to the Duplicate Versions rule; combining Games; moving a ROM to another Game after its Match (other than Splitting a Version off a Game with Duplicate Versions); making a Game into a Bundle, or a Bundle by hand, in the app; ScreenScraper media (manuals); back, cart and disc scans; showing Screenshots and Cover art (they're stored, not yet shown).

## Decisions so far

### Architecture
- SwiftUI app plus the `LudeumCore` Swift package, with GRDB/SQLite for storage ([ADR 0003](adr/0003-swiftui-not-go.md)). The `ludeum-import` CLI exists for development tasks.
- The journal owns its data and reads ROMs straight from ROM folders, one per Platform. OpenEmu is gone ([ADR 0009](adr/0009-ludeum-reads-rom-folders-openemu-is-gone.md), superseding [ADR 0001](adr/0001-journal-owns-data-one-way-sync-to-openemu.md)).
- One Mac, and one fixed layout with no location settings ([ADR 0010](adr/0010-a-fixed-data-folder-linked-into-dropbox.md)). The Ludeum folder, `~/Library/Application Support/Ludeum/`, holds the live journal database (local, never synced) and the **Data folder**, `Data/`: the ROM folders under `ROMs/<Platform>/`, [Attachments](#attachments)' files under `Attachments/<Platform>/<Game>/`, the [Backups](#backups) under `Backups/`, what DuckStation keeps under `Emulators/DuckStation/` (its [save states](#playing-in-an-emulator) and memory cards, BIOS, game settings, input profiles and screenshots), and `OpenEmu Battery Saves archive/`. The DuckStation Ludeum installs sits beside the journal, outside the Data folder, as `Emulators/DuckStation.app` ([ADR 0024](adr/0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md)). I replace `Data` by hand with a symlink to `~/Dropbox/games/Ludeum`; nothing in Ludeum depends on where it links. The cache lives apart in `~/Library/Caches/Ludeum/`, excluded from backups; one left in the Ludeum folder by an older build is ignored and rebuilt.
- **Nothing works until the Data folder is found.** Missing, or a link to somewhere that isn't there, the app opens no journal and runs no Import or backup: a sheet blocks the window, says how to fix it (create the folder, or link it) and has Check again (it's checked again whenever Ludeum comes to the front, too). Every `ludeum-import` command refuses with the same words. Ludeum never creates `Data` itself, so it can't quietly replace a missing link with an empty local folder; inside an existing one it creates `ROMs/` and `Backups/` when they're missing, and each Platform's folder when it's first needed.
- **A journal that won't open blocks the window too**, saying why, with Try again and Quit: an empty Library in its place would look as if the journal were lost. It's only tried again when asked, since opening it can take a backup first.
- Credentials live in the Keychain (see [Settings and credentials](#settings-and-credentials)). `.env` is only for the CLI and tests (see `scripts/setup-igdb.sh`).

### App skeleton
- **Project shape:** XcodeGen. A `project.yml` defines the app target, which depends on the local package's `LudeumCore`. The generated `.xcodeproj` is gitignored. The app target sets warnings as errors, CI installs XcodeGen with brew, and the `swift build -warnings-as-errors` job stays.
- **Signing:** the free Personal Team ("Apple Development"), a stable identity, so the Dropbox access prompt and Keychain access survive rebuilds. No restricted entitlements, so the 7-day profile expiry never matters. Keychain items use the file-based keychain, which needs no profile.
- **No App Sandbox.** It's a personal app that reads and writes ROM folders in Dropbox and opens other apps (the Emulators), so the sandbox would add friction (security-scoped bookmarks or exception entitlements) without protecting anything.
- **Where work runs:** in-process. The app calls `LudeumCore` from structured tasks off the main actor. `ludeum-import` stays a dev tool over the same `LudeumCore` calls; the app never depends on it. There's no helper, so nothing runs while the app is closed.
- **When background work runs:** only while the app is open. On launch, a low-priority refresh of expired cache entries, plus the daily backup if one is due. Covers are fetched on demand. Import runs at launch and when I start it.
- **Overlap:** one Import runs at a time. The background refresh pauses during it, since they share the rate limiters. Editing the journal is allowed during the refresh, but not during the Import's write step. The app keeps one client per service (IGDB, Hasheous) for every screen, the Import and the refresh, so each service's rate limit holds across all of them; IGDB's images don't wait their turn at it. A ROM whose files were read again while the Import ran (its Archive, Unarchive or Compact finished) stays as it was read then: the Import's own reading of its folder is the older one.
- **The Library's IGDB facts** (genres, themes, companies, release year, players) are read from each linked Game's cached record once, kept across journal edits and shared by every screen showing them: only Games linked since are read, and a Game's are read again once its record has been fetched again (by the launch refresh, an Import or a search). A read that fails isn't kept as no facts: the next ask tries again, and the facts read so far show until it works.
- **Progress and interruption:**
  - Import has no screen of its own: it runs in the background and writes in one transaction at the end, so stopping it part-way writes nothing. Lookups already made survive in the cache, so a rerun is quick. Quitting mid-Import asks first.
  - The background refresh shows only a small status indicator. Its errors are logged, not shown as alerts.

### Games and identity
- A Game is a title on one Platform. It can have one IGDB link or none ([ADR 0002](adr/0002-game-identity-is-journal-owned.md)).
- Regions, revisions and fan translations belong to the same Game. Ports, and enhanced re-releases that IGDB lists separately, are separate Games.
- Platform means the platform the Game was made for. How I played it (MesenCE, Switch Online, Steam Deck, …) is a Playthrough's "Played via".
- **Platforms are IGDB's platforms** ([ADR 0005](adr/0005-platforms-are-igdb-platforms.md)): the list comes from IGDB's `platforms` endpoint, cached like any other record. Every Game has one, including Games with no IGDB link. There are no custom Platforms.
- **An IGDB link is unique:** no two Games share the same IGDB game and Platform. Its platform is always the Game's Platform, even when IGDB doesn't list that game on it.
- Display name: IGDB's name, which I can override. Games without an IGDB link use a cleaned No-Intro name, or the name I typed.

### Adding Games
Non-emulated Games (PC, Xbox 360, …) and Games I don't have a ROM for yet are added by hand.

- **Platform picker:** every IGDB platform, type-to-filter, with Platforms my Games already use listed first.
- **Searching IGDB:** one search box, a Base games / Expansions toggle (Base games each time the search appears), and an optional Platform filter, empty by default. Each result is an IGDB game with its cover, name, first release year, `game_type` (when it isn't a main game) and its platforms as chips, and an Expansion's "Expansion of ‹IGDB's name for its `parent_game`›" under them. Base games never include DLC (1), Expansion (2), Season (7), Pack/Addon (13) or Update (14); Standalone Expansions (4) and Mods (5) are shown and labelled. Expansions are only DLC (1), Expansion (2) and Standalone Expansion (4): IGDB's line between DLC and Expansion is fuzzy (Cuphead's The Delicious Last Course is DLC). The toggle is the same wherever the search is: the IGDB screen, Link to IGDB…, the Review queue's search and Add ROM.
- **Expansions:** a Game whose IGDB link is DLC, an Expansion or a Standalone Expansion. Under its name in Game detail, "Expansion of ‹Base game›": a link to my Game on the same Platform holding IGDB's `parent_game`, by my name for it, else IGDB's name unlinked, or just "Expansion" when IGDB has no `parent_game`. A Base game's Game detail lists "Expansions:" the Games on its Platform holding one of IGDB's `expansions`, `standalone_expansions` or `dlcs`, each a link. Nothing about it is stored: it's read from the linked IGDB record, so a hand-made Game is never one. Matching is unchanged: a name search never suggests DLC (1) or an Expansion (2), though a Standalone Expansion (4) can be, as before.
- **The IGDB screen:** a sidebar screen (the toolbar's Add Game button opens it) with the search and its results in the middle column. Results sort by name (A–Z, the default) or release date (newest first), undated last, and a result already in the Library is marked "In Library" with its Platforms ticked. Selecting a result shows the IGDB game in full in the detail column: cover, year, type, its platforms, then Game detail's IGDB facts and Screenshots. Clicking a Screenshot opens a gallery (`ScreenshotGallery`): IGDB's `original` of each, never cropped and never shown bigger than its own size in pixels, except that one under 200 pixels either way is scaled up by the least whole amount that takes its shorter side to 200 (`screenshotScale`: a Game Boy's 160 × 144 shows at 320 × 288), without smoothing, so its pixels stay sharp; ← and → or the arrows over it to go back and on (round from the last to the first), a strip of every Screenshot, in the tiles' shape, to click through, and Close. Both pages show IGDB's summary (four lines, then More), time to beat, a Trailer link (the first video IGDB calls a trailer) and its keywords at the foot; Library search also matches keywords.
- **Choosing the Platform:** in the IGDB game's detail, clicking a platform adds the Game to the Library on that Platform. A "Different platform…" chip opens the Platform picker, for ports IGDB doesn't list, and the IGDB link then records that game on my Platform. One Game per add: playing it on another Platform means adding it again.
- **After adding:** the Game takes IGDB's name, Cover and link. The IGDB page stays open and the platform turns "In Library", so I can keep browsing. Nothing else is asked up front.
- **No duplicate IGDB links:** a chip whose IGDB game and Platform already belong to a Game is marked "In Library", and clicking it opens that Game. Platforms not listed by IGDB that a Game holds this link on (added with "Different platform…") are shown too. A ROM Added later (a Stray file, or by Add without a Match) whose match is that IGDB game joins that Game rather than creating a new one.
- **Creating a Game by hand** (no IGDB link): "Add by hand" at the foot of the IGDB screen, with the name pre-filled from the search box. Name and Platform are required. A Cover upload is optional, and everything else is edited in Game detail.
- **Duplicate warning for hand-made Games:** if a Game on the same Platform has a name that *agrees* (the matching normalisation, against its display name and its IGDB names), I'm asked to **Open** it or **Add anyway**. It warns and never blocks, because two games on one platform can share a name.
- **Linking a hand-made Game later:** a Game with no IGDB link can gain one through the same search, filtered to its Platform. Its name then follows IGDB unless I've overridden it, and its Cover becomes IGDB's. If another Game already holds that link, it's refused ("Already linked to X"), since combining Games is a non-goal. An existing link can be changed (Edit → Change IGDB link…) to fix a mistaken Match, under the same rule; it's never removed.
- **One search component:** the Review queue's manual IGDB search is this same search. There, the Platform filter is pre-set to the ROM's platforms, and clicking a result Matches the ROM instead of adding a Game.
- **A hand-made Game created from a ROM** (Review queue, no suggestion): its Platform is pre-selected from the ROM's (its ROM folder's), and I can still pick any other Platform.

### Bundles
A Bundle is one release of several games that were each also released on their own ([ADR 0016](adr/0016-a-bundle-is-not-a-game.md)).

- **Not a Game:** it's never a Library row, nor counted on its Platform in the sidebar. Its Games are, on its Platform. Its page is Game detail without My journal or Play: its Cover, IGDB facts, Highlight note, Copies, Attachments and a **Contains** section listing its Games as links, each with Remove, and **Add Game…** (one IGDB lists for it, added to the Library if need be, or any Game of its Platform in the Library).
- **Adding one:** in the IGDB screen, a result IGDB types a bundle opens a sheet on choosing its Platform: IGDB's contents for it (`where bundles = (id)`), every one ticked, each already in the Library marked so and linked rather than added. **Add Bundle** is the default; **Add as a Game Instead** is for a release that's one game (Kirby Super Star).
- **Its Copies are its Games' Copies:** each Game shows them under its own Copies, each like one of its own but titled "‹type› (from ‹Bundle›)" (a click opens the Bundle, where they're edited), and is Owned (as a ROM, for a ROM) by them. Play opens the Game's own ROM first, else a Bundle's, with the Game's Emulator settings, from Game detail and the Library. A Playthrough can name a Bundle's Copy. Duplicate Versions counts only a Game's own ROMs.
- **Shown on its Games:** "Bundled in: ‹Bundle›" under the Platform line, its Highlight note (prefixed with its name), and its Attachments in their own section, opened there and managed on the Bundle. A Game with no upload or Box art shows the first Bundle's Cover, ahead of its own IGDB Cover art; if the Bundle has none, its own Cover art shows.
- **Search** matches a Bundle's name to its Games.
- **Matching:** a ROM whose IGDB game is a Bundle in the journal is Matched to the Bundle. Otherwise a Game is made, as before.
- **Deleting:** a Bundle can't be deleted while it has a Copy; its Games stay. A Game can't be deleted while a Bundle contains it, and can't leave one while a Playthrough of it names one of the Bundle's Copies.
- **Games that were really Bundles** were made into Bundles once, by hand with Ludeum closed, by `ludeum-import into-bundles`, which went once it had run (its `before-into-bundles` backup is kept forever).

### Journal data
- **Rating:** 0.0–10.0, or unrated (different from 0.0). One per Game, with a Rating history of dated entries.
- **Rating history:** at most one entry per day (local time). Changing the Rating again the same day replaces that day's entry, and re-entering the current value does nothing. Clearing a Rating adds an "unrated" entry. Entries can be deleted but not edited, so there's no backdating. Deleting the latest entry makes the previous one the Rating.
- **Playthrough:** **a start date is required**; every other field is optional (end as a Partial date, Outcome of Finished or Dropped, notes, Version, Played via). A Playthrough with no Outcome is in progress. **The end date can't come before the start date**, compared with the Partial date sort, and a less precise date is allowed when it contains the other (start `2024-03`, end `2024` is fine; end `2023` is refused on save). Version and Played via are free text, with suggestions drawn from the Game's ROM names.
- **Intent:** none, Backlog, Up next, or Want to buy (a set, not ordered). Want to buy is for a Game I don't own yet: it isn't What to play next, and has its own sidebar screen, **Want to buy**, after What to play next: the Library scoped to it, like Finished and Childhood. A Want to buy Game's Cover shows a blue cart at its top right (unless it's Playing or Finished, whose badges sit there instead). It doesn't depend on Playthroughs. The date and time it was set is recorded (never edited by hand): changing the value resets it, clearing Intent drops it, and setting the same value again does nothing. Intent brought over by the first Import, from OpenEmu, is undated.
- **Partial dates sort** as if the missing parts came first: `2024` < `2024-01` < `2024-01-05`.
- **Childhood:** a flag on a Game.
- **Copies** ([ADR 0011](adr/0011-roms-are-copies.md)): a Game has any number. Each is one of four Kinds: a ROM, or one recorded by hand as Physical, Digital or Physical + digital (an Xbox disc with its linked digital licence is one Copy). Every Copy, ROMs included, has the same optional details: Regions (any text, zero or more, with Europe, USA, World, Australia, Japan and Asia offered first and then any other I've used, shown in that order), acquired on (a Partial date), acquired from (free text), a price (a decimal amount in a 3-letter currency, AUD unless I say otherwise) and Notes (free text, e.g. that a disc can't be traded in for a digital licence). A hand-recorded Copy can be marked **no longer owned** (Gone), with where it went and when, a Partial date that can't come before it was acquired (a less precise date that contains the other is fine); it's kept, and can be made Owned again. A ROM is never Gone: it leaves only by being deleted. A ROM's Regions are read from its name's tags when it first appears (No-Intro names as written, GoodTools codes spelled out: `(UE)` is USA and Europe); the `v22` migration did the same for every ROM already in the journal. A PlayStation ROM whose name has no region tag takes the Regions its Discs' Serials say ([ADR 0025](adr/0025-a-playstation-roms-serials-say-its-regions-before-hasheous.md)): each Serial's prefix gives one (`SLUS`, `SCUS` USA; `SLES`, `SCES`, `SLED`, `SCED` Europe; `SLPS`, `SCPM`, `SIPS`, `PCPX` Japan; `SLKA` Korea), each once; one whose Serials aren't read yet waits for them. Any other ROM with no region tag, or one whose Serials give none, takes the Regions of the DAT entry its checksum is in Hasheous ([ADR 0019](adr/0019-a-rom-with-no-region-tag-takes-its-regions-from-hasheous.md)): the region tags of the entry's name (`Super Metroid (Japan, USA) (En).sfc`), else the countries Hasheous lists for it (TOSEC's `(EU-US)`). It's given Regions once, at the next Import (after its Serials step) or when it's Added, whether or not either knows them; one with neither Serials that say them nor a checksum isn't, nor one whose Copy details I've edited, so Regions I clear stay cleared; `v37` first reads again the names of ROMs with none, for tags `v22` couldn't read (GoodTools' `(UEJ)`). A lookup that fails is tried again at the next Import; after three in a row fail, the rest wait for it too. Otherwise a ROM's Regions are never touched again. A ROM's Copy details live on the ROM and go with it through any change of Match, so an unmatched ROM is a Copy of no Game and Split loses nothing. Playthroughs and Copies never look at each other: I play on friends' Copies.
- **Owned:** a Game with a Copy that isn't Gone. Since a ROM is a Copy, a Game with a ROM is Owned whether the ROM is present or missing (a missing file is an error to fix, not a Copy I've lost). The Library's **Owned** filter offers Owned, Owned as a ROM (it has one), Owned only as a non-ROM Copy (hand-recorded Copies, no ROM) and Not owned (no Copy that isn't Gone); it combines with the ROMs filter (Playable, Archived). A Not owned Game is a plain journal entry, there because I'm interested in it or have something to record, and nothing about it needs fixing. Want to buy stays an Intent and is never changed by Copies: a Want to buy Game I've since bought shows both the cart and the Not owned book until I record the Copy or change the Intent.
- **Cover:** my upload, else LaunchBox Box art, else the first Bundle's Cover, else IGDB's Cover art, else a placeholder. See [Covers](#covers).

### Journal database schema
GRDB over SQLite, with foreign keys on. Table and column names are as they'll appear in `LudeumCore`.

- **Conventions:** integer `INTEGER PRIMARY KEY` ids. A Partial date is one text column (`1996`, `1996-03`, `1996-03-17`, CHECKed for shape), so plain string order is the Partial date sort and "contains" is a prefix test. Timestamps are ISO-8601 UTC text (GRDB's `Date` encoding). Every table has `createdAt` and `updatedAt`, kept by triggers ([ADR 0015](adr/0015-every-row-has-created-and-updated-timestamps-kept-by-triggers.md)). A Rating history day is the local date as `YYYY-MM-DD` text. Ratings are integer tenths (0–100).
- **`platform`** (IGDB platform id, name): copied from IGDB so names show without the cache.
- **`game.runAheadFrames`** (nullable integer, 0–10): the Game's own Emulator setting.
- **`game.gameBoyModel`** (nullable text: `gameBoy`, `gameBoyColor`, `superGameBoy`; null is Auto): the Game Boy Model, for Game Boy and Game Boy Color Games.
- **`game.cdReadSpeedup`** (nullable integer, 0–6, DuckStation's `ReadSpeedup`: 1 off, 2–6 times, 0 maximum; null is DuckStation's own setting): the CD read speedup, for PlayStation Games.
- **`game.cdSeekSpeedup`** (`v41`; nullable integer, 0–6, DuckStation's `SeekSpeedup`, numbered as `cdReadSpeedup`; null is DuckStation's own setting): the CD seek speedup, for PlayStation Games.
- **`game`**: `platformId` (required), `igdbGameId` (nullable, `UNIQUE(igdbGameId, platformId)`, set at most once), `igdbName` (refreshed with the cache record), `name` (hand-made or cleaned No-Intro) and `nameOverride`. The display name is `nameOverride ?? igdbName ?? name`, so the database alone (a backup, a cold cache) shows every name. Also `childhood`, `intent` (backlog/upNext, or null) and `intentSetAt` (null when undated). Intent keeps no history.
- **The current Rating is derived**, never stored: it's the latest `ratingEntry`.
- **`ratingEntry`**: `gameId`, `day`, `rating` (NULL = cleared to unrated), `UNIQUE(gameId, day)`.
- **`playthrough`**: `gameId`, `start`, `end`, `outcome` (finished/dropped, or null), `notes`, `version`, `playedVia`. `start` is NOT NULL (since `v9`). End ≥ start is checked in app code.
- **`battle`** (`gameAId`, `gameBId`, `result` a/b/same, `day`), **`battleSkip`** (`gameAId`, `gameBId`, `day`) and **`keptRating`** (`gameId` PK, `afterBattleId`: set aside until a later Battle). All cascade with their Games. Days are local `YYYY-MM-DD`, like Rating history's.
- **`cover`**: `gameId` as PK, `jpeg` BLOB, width, height, `sha256`. It holds uploads only.
- **`rom`**: one row per ROM in a ROM folder: `platformId` and `folderName` (its name in the folder, `UNIQUE(platformId, folderName)`), an optional checksum, `md5` or `crc` (see ROM folders' Checksums; migrated ROMs kept OpenEmu's MD5 until `ludeum-import checksums` put them right), `fileName`, `name` (from the file name), `missing`, `archived`, `version` text, `discNumber`, `discLabel`, `needsPlaylist` (its subfolder holds Discs but no playlist), `inBothForms` (its ROM folder keeps it in more than one form), and its Copy details (`v22`): `regions` (a JSON array of names, or null), `acquiredOn` (a Partial date), `acquiredFrom`, `price` (a decimal as text) and `currency` (both set or both null), and `notes` (`v32`), plus `regionsLookedUp` (`v37`: whether its checksum has been looked up for Regions, or I've edited its Copy details), and its Serials (`v40`): `serials` (a JSON array in Disc order, null for a Disc with none, or null when no Disc has one) and `serialsLookedUp` (whether they've been read off its Discs). `v38` dropped the libretro-thumbnails names each ROM kept ([ADR 0020](adr/0020-launchbox-is-the-only-source-of-box-art.md)). **The Match is columns on the ROM:** `gameId`, `matchKind` (automatic/confirmed/manual) and `matchedAt` are all null or all set (CHECK). An unmatched ROM is in the Review queue.
- **`copy`** (`v22`): a hand-recorded Copy: `gameId` (cascades with its Game), `kind` (physical/digital/physicalAndDigital), the same Copy details as a ROM's, and `gone` with `goneOn` (a Partial date) and `goneTo`, which are null unless `gone` (CHECK). Gone on ≥ acquired on is checked in app code, like a Playthrough's dates.
- **`attachment`** (`v30`): `gameId` (cascades with its Game), `fileName` (its file's name, extension and all; `UNIQUE(gameId, fileName)`, case-insensitive), `manual` and `missing`. **`game.attachmentFolder`** is the Game's folder's path in `Attachments/` (`SNES/Super Metroid`), unique case-insensitively, null until it has one.
- **`game.bundle`** and **`bundleGame`** (`v35`): a Bundle is a `game` row marked as one; `bundleGame` (`bundleId` cascades with the Bundle, `gameId` restricts deleting the Game) says which Games it contains.
- **Review queue suggestions are stored** on the ROM when the Import writes (`suggestedIgdbGameId`, `suggestionKind` checksum/name, `checksumIgdbGameId` for the crossed-out checksum game, `namesAgree`) and cleared on matching. Opening the queue makes no IGDB calls.
- **`import`** (`startedAt`, `isFirst`). There is no Activity (ADR 0007).
- **`heldOpenEmuData`** held an unmatched ROM's OpenEmu collections and `_Current` start date answer, captured by the first Import (from OpenEmu) and applied when the Review queue resolved the ROM. Once none were left it went (`v33`): an answer applies nothing more. Sync's `syncedCollection`, `syncedCover` and `openEmuLibrary` went with OpenEmu.
- **Deleting a Game** relies on `ON DELETE CASCADE` all the way down (Rating history, Playthroughs, Cover, Copies). The app refuses before that while the Game has any Copy.
- **Migrations:** GRDB's `DatabaseMigrator`, like the cache. There's one `v1` migration, edited freely until the first real Import into the production database, then append-only, with a backup before migrating. `eraseDatabaseOnSchemaChange` is for development only. `v16 no openemu` (OpenEmu's columns and tables go, `folderName` becomes required) refuses a journal that still has OpenEmu ROMs rather than lose one, so it doesn't open (see [Migrating from OpenEmu](#migrating-from-openemu)).

### Deleting
- **A Game with any Copy can't be deleted**: a ROM, present or missing, or a hand-recorded Copy, Owned or Gone. The UI says to delete them first, under Copies. Only a plain journal entry can go. There's no "ignored ROM": an unwanted ROM is deleted, which sends its files to the Trash.
- **Deleting a Game** hard-deletes all its journal data (Rating history, Playthroughs, Intent, Childhood, IGDB link, uploaded Cover), and sends its Attachments' files to the Trash once the backup is taken (`Attachments.deleteGame`), leaving anything else in their folder; the confirmation says how many Attachments go.
- **Deleting a Copy** is one verb for every Kind, and is for good, unlike marking a hand-recorded Copy no longer owned. **Deleting a ROM** (`LudeumStore.deleteROM`), Matched or not, from Game detail or the Review queue: a present one's files go to the Trash first (its subfolder whole, with any `.7z` or Compacted copy), after a confirmation that says so and a backup; a missing one just leaves the journal. Its Copy details go with it; if its file comes back, a later Import lists it as a Stray file, to Add afresh. Refused, with nothing sent to the Trash, when it's present but its files aren't in its ROM folder; if sending them fails part-way, the journal sees what's left, and the ROM goes only if all of it reached the Trash. Disabled while a Background task is queued or working on it. Nothing deletes a ROM on its own: a missing file is an alert until I put one back or delete the ROM.
- **Games whose ROMs are all missing** stay as normal Games. They're never hidden or deleted automatically, but each waits in the Review queue under Missing ROMs until a ROM comes back or I delete its missing ROMs. A missing ROM of a Game that still has a present one waits under Old missing ROMs until it comes back or I delete it.
- **No soft delete or undo.** Deleting a Game, Playthrough, Copy or present ROM asks for a confirmation that says what goes with it. The automatic backups are the safety net.

### Import
- Reads the ROM folders (see [ROM folders](#rom-folders)). Never writes to them.
- Import brings in ROMs only. Intent and Playthroughs are only ever entered in the journal.
- **Matching** (confirmed in the dry run of the first Import, from OpenEmu, on the `prototype/first-import` branch; rules measured on `prototype/matching-rules`). A ROM with no checksum (see ROM folders' Checksums) skips the checksum steps and goes to the Review queue, with a name suggestion where there is one:
  1. Hasheous lookup by the ROM's MD5, else its CRC32.
  2. It's an **Automatic** Match only when the checksum *and* the name agree ([ADR 0004](adr/0004-automatic-match-needs-checksum-and-name.md)). An IGDB Bundle (`game_type` 3) is treated like any other game: single-cartridge collections (Super Mario Advance, Kirby Super Star, Super Mario All-Stars) really are Bundle records, and the name rule already keeps out wrong multi-game packs.
  3. Everything else goes to the **Review queue**, with one suggestion or none:
     - If the checksum's names disagree, a **related record** of the checksum's game whose name agrees (`parent_game`, `version_parent`, `expanded_games`, `remasters`, `remakes`, `ports`, `standalone_expansions`, `forks`) is the suggestion, e.g. *Resident Evil 2: Dual Shock Ver.* for a checksum pointing at *Resident Evil 2*. Otherwise the checksum's own game is.
     - With no checksum game, IGDB name search on the ROM's platforms. The suggestion is the first candidate whose name agrees, else the first candidate. Candidates of `game_type` Mod (5), DLC (1), Expansion (2), Season (7), Pack/Addon (13) and Update (14) are never suggested.
     - Otherwise no suggestion (search IGDB by hand).
  4. The Review queue showed whether a suggestion's names agree, and could bulk-confirm those that did; Confirm all went once the first Import's had been answered, as ROMs now reach the queue one or two at a time.
  5. Measured on my OpenEmu library before the first Import: about 907 Automatic, about 223 of 224 name suggestions bulk-confirmable, about 35 with nothing. That leaves about 30 checksum suggestions (4 of them bulk-confirmable through a related record), 1 name suggestion and 35 manual searches.
- **Names agree** when any ROM-side name equals any IGDB-side name after normalising. Never prefix or containment: nearly every wrong checksum match is the IGDB name being a prefix of the ROM's title (*Super Star Wars* for *Super Star Wars: Return of the Jedi*).
  - ROM side: the ROM's name. Bracketed groups are removed. A ` ~ ` separates alternative titles. Title and subtitle may be swapped (`Super Mario Advance 2 - Super Mario World`). File artefacts are removed: `.nkit`, `.sav`, trailing copy numbers, `-redump`, `# GBA`, patch suffixes, leading scene release numbers, and for bracket-free homebrew names underscores and a trailing version (`Feed_IT_Souls_v1.4`).
  - IGDB side: the game's `name`, every `alternative_names[].name` (acronyms included) and every named `game_localizations[]`. An alt name whose comment starts "Japanese", "European", "Korean" or "(North) American", and a Japan, Europe or Korea localization, only count for a ROM from that region (or of unknown region), so *Lilo & Stitch 2*'s Japanese title "Lilo & Stitch" doesn't match a USA *Lilo & Stitch*.
  - Normalising: lowercase; fold diacritics; `&` → `and`; split into words on anything but letters and digits; roman numerals II–XX become digits (not I, V or X); drop `and`, every `the`, and a leading `a`/`an`; drop a leading `Disney's`, `Disney-Pixar's`, `James Bond`, `Tom Clancy's` or `Sid Meier's`; join the words.
- **Versions** aren't parsed into fields. A Version is described by the ROM name's tags as written (region, languages, revision, dev status, translation and so on), without the Disc and its label, GoodTools dump flags (`[!]`, `[a]`, `[b]`…) and file artefacts. Real names mix No-Intro, Redump, GoodTools, scene and ad-hoc forms, and a Version is only ever shown or suggested as text.
- **Discs:** the present ROMs of one Game that each carry a `(Disc N)` (or, in a floppy set, a `(Disk N)`), with no number repeated, are the Discs of one Version, whatever else their names say (Gran Turismo 2's two Discs come from different DAT versions). An `.m3u` playlist ROM of that Game belongs to the same Version. The free-form flag straight after `(Disc N)` is the Disc label, unless it's a tag of the Version (`v1.1`, a revision, languages): Metal Gear Solid's `(Disc 1) (v1.1)` has none. On the disc Platforms, a multi-disc Version is instead one ROM: a subfolder holding its playlist and Discs (see Disc ROMs into folders).
- **Duplicate Versions** (2 or more *present* ROMs on one Game that aren't Discs of one Version) go to the Review queue: the Game keeps its journal data and stays editable, and the item stays until the Game has one Version left: I Keep only one Version, Split one into its own Game, or remove ROMs from its ROM folder. There's no exceptions mechanism, and the UI says real exceptions need a code change. My OpenEmu library had 2 at the first Import: Double Dragon III (Japan and USA) and Sweet Home (two translations).
- **The first Import**, from OpenEmu, was staged as an Import draft and committed once, in one step, with my start dates for `_Current` games. It's done, and went with OpenEmu: its unmatched ROMs carried over into the Review queue with their OpenEmu data held (`heldOpenEmuData`, gone since they were all answered), and OpenEmu's orphaned entries (150, 60 holding data) became missing ROMs.
- **The journal says which ROMs there are** ([ADR 0017](adr/0017-the-journal-says-which-roms-there-are.md)). A file in a ROM folder that isn't a ROM is a **Stray file**: the Import keeps a list of each folder's, rewritten once it has read the folder (a folder it can't read keeps its list), and makes a ROM of one only when asked to add it: by Add without a Match, which hands it exactly the ROMs it put in, or by Add as ROM (or Add all) in the Review queue.
- **Each Import:** new ROMs (Stray files it was asked to add) go through matching. A ROM whose files are all gone is marked missing; one that comes back rejoins its old Game with its old Match, without review. A new ROM (or a Review queue answer) that gives an existing Game Duplicate Versions is still Matched, and the Game gets a Duplicate Versions item in the Review queue. Each Import re-checks it.
  - **When it runs:** at app launch, with the Review queue's Check again, Add as ROM and Add all, and after Add without a Match (a request mid-Import runs once more afterwards, adding everything either was asked to add). The journal never watches the folders.
  - **What I'm told:** Automatic Matches are added silently. The Review queue carries a count badge. After an Import that changed something, a dismissible in-app summary lists ROMs sent to review and gone missing (linking to their Games), and files that have turned up as Stray files since the last Import (one already listed isn't told again). An Import that changed nothing shows nothing. A failed Import says why, dismissibly. No system notifications.

### ROM folders

- **A ROM folder** holds one Platform's ROMs, and the folder alone gives a ROM its Platform. Every Platform with an Emulator has one, strictly one per IGDB Platform: Game Boy and Game Boy Color, NES and Famicom, SNES and Super Famicom each have their own (`ROMPlatform.all`). Each is named for its Platform under `ROMs/` in the Data folder (`PS2`, `SNES`, `Game Boy Color`, `Famicom`, `PS1`…), PS2's included; none is a setting. Every Import reads all of them; a folder that can't be read is skipped, leaving its ROMs and Stray files alone. Hidden folders are ignored.
- **Files:** what the Platform's Emulator opens is ready (for PS2, what PCSX2 opens: `.iso`, `.chd`, `.cso`, `.zso`, `.gz`, `.cue`, `.bin`, `.mdf`, preferred in that order). Where the Emulator opens an archive directly, that archive is ready too, after every loose format: a `.7z` for MesenCE's cartridge Platforms (NES, Famicom, SNES, Super Famicom, Game Boy, Game Boy Color, GBA, Master System, Game Gear) and melonDS's DS, a `.zip` for ares's N64 and Mega Drive (ares can't open a `.7z`). Checked in MesenCE's and melonDS's source: an archive holding one ROM loads without asking. Vita's are `.vpk`s, which no Emulator plays yet. Xbox's are `.iso`s, which xemu boots only as an XISO (the game partition alone), not a full Redump image ([research](research/xbox-emulator.md)); the ROM folder reads either as a ROM, and Play tells them apart. Wii's are WiiWare and Virtual Console `.wad`s, then disc images (`.rvz`, `.wbfs`, `.iso`, `.wia`, `.gcz`, `.ciso`); Dolphin's `-e` boots a `.wad` by installing it into its emulated NAND as a temporary title, so nothing is installed first ([research](research/wii-emulator.md)). Untested: Playing a DLC `.wad` (a title to install, not play), or a `.wad` whose title Dolphin already has in another version, which asks mid-Play whether to replace it. Any other `.7z` is **Archived**; anything else, including `.rar` (and `.zip` off ares), is ignored. A cue sheet's `FILE` tracks belong to it. A subfolder is a ready ROM named after itself when it holds one playlist, else one cue sheet, else one image, else Discs without a playlist, at any depth, whatever else is in it; a subfolder of the same name wins over a loose file.
- **Identity:** a ROM is its file name without the extension, or its subfolder's name (`rom.folderName`, unique per Platform). Unarchiving, Archiving or Compacting changes one ROM's file silently, keeping its Match; when both files exist the ready one is used (a loose file over its Compacted copy). A ROM whose files are all gone is missing.
- **Checksums** ([#50](https://github.com/danielholmes/ludeum/issues/50)): each Import gives a new ROM a checksum for matching, and so does an unmatched ROM that has none yet (one imported before ROMs had them, or while its file was online-only or 7-Zip was missing), which is then matched again. A ROM that has one isn't hashed or looked up again. The MD5s OpenEmu's migration carried over (a disc's of its cue sheet, which no DAT has) were put right once, by hand with Ludeum closed, by `ludeum-import checksums` ([#80](https://github.com/danielholmes/ludeum/issues/80), ADR 0025), which went once it had run (its `before-checksums` backups are kept forever): each ROM present in its ROM folder was read as a new one is, and where that differed from what the journal held the new checksum replaced both old values, a form no DAT knows had its cleared, and one with no Regions was given them again at the next Import; one kept online only was left for a later run. Rehearsed on a copy of my journal on 2026-10-28: 1,122 of 1,241 present ROMs changed (1,102 OpenEmu MD5s to their archive's CRC32, 2 to their data track's MD5, 18 with none given a CRC32), 74 online-only were left, and the next Regions step gave all 68 PlayStation ROMs without Regions USA from their Serials. On my library it ran four times on 2026-10-28 as Dropbox brought files down, the last with none left online only; four PlayStation ROMs an Import before ADR 0025 had looked up at Hasheous, finding nothing, were set to be looked up again by hand.
- **Serials** ([ADR 0021](adr/0021-duckstation-settings-go-in-its-per-game-file-named-by-the-discs-serial.md)): each Import reads the Serials of every PlayStation ROM that hasn't had them read, before the Regions step (they give a ROM its Regions ahead of Hasheous, ADR 0025), and so does Add ROM for the one it puts in: one per Disc, in its playlist's order, off the Disc's data track (a cue sheet's first track, or the image), from the ROM folder or streamed out of its `.7z` with nothing written. A Disc's Serial is what DuckStation names it: the executable its `SYSTEM.CNF`'s `BOOT` line boots (`cdrom:\SLUS_005.51;1`, or with no backslash), its file name upper-cased, without dots and with `_` as `-` (`SLUS-00551`), as long as it's on the disc. With no `SYSTEM.CNF` or `BOOT` line, `PSX.EXE`, or an executable that isn't there, DuckStation goes by a hash of it, and the Disc has none. A ROM is read once, whatever its Discs say; one kept online only, in a form not read yet (`.chd`, `.pbp`), in a `.7z` with no 7-Zip, or that fails to read is left for the next Import. Its Serials stay through a Rename, an Archive and an Unarchive, and go when its dump does: giving a missing ROM a Stray file, or Add ROM bringing a missing ROM back, has them read again. In a `.7z`, a playlist's Discs are found by their `(Disc N)` names and a cue sheet's data track by its own name or as `(Track 1)`, where they say, since 7-Zip packs the text files after the images; only as much of a track is unpacked as its layout needs (`SYSTEM.CNF` can be near the end). The first Import after `v40` reads every PlayStation ROM: about 9 minutes for my 113. They show beside its Regions on Game detail, and can't be edited.
  - A loose ROM is the **MD5** of the file the DATs hash: a playlist's first Disc, a cue sheet's first (data) track, else the file itself, with an iNES or FDS header (16 bytes) and, on the SNES and Super Famicom, a copier header (512 bytes) left out, as No-Intro does. Every file is hashed, a PS2 ISO included; it takes seconds.
  - A ROM in a `.7z` or `.zip` (Archived or Compacted) is the **CRC32** in the archive's index, of its largest file other than a playlist or cue sheet, so nothing is unpacked. Without 7-Zip it has none.
  - Images no DAT has a hash for (`.chd`, `.rvz`, `.wia`, `.cso`, `.zso`, `.gz`, `.gcz`, `.wbfs`, `.ciso`, `.pbp`) have none, and neither does a file Dropbox keeps online-only, which isn't downloaded for it. A ROM with none is only ever suggested by name.
- **Archived:** present, so it counts against deleting its Game, but there's nothing to Play: Game detail shows "Archived: unarchive to play" with **Unarchive** (or, on N64 and Mega Drive, "Archived: compact to play" with **Compact**).
- **Archive / Unarchive** (PS2, PSP, Vita, GameCube, Wii, Xbox and the disc Platforms: PS1, Sega CD, Saturn, PC Engine CD) and **Compact** (the Platforms with a ready archive), on each present ROM in Game detail, run as Background tasks with Homebrew's 7-Zip (`7zz`; without it they say to `brew install sevenzip`). It's optional: at launch, if it isn't installed, a warning says what needs it and how to install it, and once dismissed Ludeum carries on as normal (`SystemTool`, `SystemToolsOnLaunch`). Work happens in a hidden `.ludeum-work` folder inside the ROM folder (cleared at launch, so an interrupted task leaves nothing behind) and moves into place only once checked; the file it replaces goes to the **Trash**, last. A task first checks there's enough free space. While one is queued, its ROM's row in Game detail shows Queued with Cancel, which takes it off the queue.
  - **Archive** packs the ROM's folder's contents (or a loose file, a cue sheet with its tracks) into `<ROM name>.7z` with `-mx=9`, runs `7zz t`, and checks the listing before trashing what it packed. A folder of the ROM's name that doesn't hold the game isn't its folder: the loose file is packed and the folder left alone. A PSP, Vita, GameCube, Wii or Xbox ROM kept in a subfolder packs just the game, leaving hidden files that aren't the game out (a `.DS_Store`; a game's own name can start with a dot), and anything else beside it refuses the Archive, as it would be lost on the way back.
  - **Unarchive** accepts any `.7z` and unpacks all of it into `<ROM name>/`, so nothing inside needs renaming and extras (a readme) come along. It reads the listing first: an archive that wouldn't make a ROM of its folder (one playlist, else one cue sheet, else one image, else Discs, as a ROM folder's subfolder is read) is refused, so a multi-disc Version with its playlist comes back as one ROM. Extracted sizes are checked against the listing before the `.7z` is trashed. PSP's, Vita's, GameCube's, Wii's and Xbox's ROMs are each one file, so their `.7z` must hold just its image (hidden files beside it, a `.DS_Store` say, are ignored), which unpacks loose as `<ROM name>.<ext>`.
  - **Compact** packs a ROM as Archive does, into `<ROM name>.7z` (or `.zip` on ares's Platforms), which its Emulator still opens. An Archived `.7z` on N64 or Mega Drive is repacked instead: unpacked in the work folder, packed as a `.zip`, tested, and its listing checked against the `.7z`'s (paths and sizes) before the `.7z` is trashed. That's how the `.7z`s brought over before Compact existed become playable.
  - When a task ends, the ROM is re-read (`checkROMAgain`), Matched or not: also when it failed or was cancelled, which can come once its files have already moved.
- **Rename** (`ROMRename`, `renameROM`), on each present ROM in Game detail whose name, before its tags, isn't its Game's, while no Background task is working on it: after a confirmation, it renames the ROM after its Game with its tags kept (`Ōkami (USA).iso` → `Okami (USA).iso`; a colon becomes " - " and a slash "-"). It's offered unless the ROM's name is already the Game's followed by nothing but tags (the Game's own name can have tags: `Foo (2008) (USA)` is Foo (2008)'s), and never for a name its ROM folder wouldn't read (starting with a dot). Everything at the top of the ROM folder with its name is renamed (`ROMMove.rename`), so nothing of it is left to be found as a new ROM: its subfolder (what's inside keeps its names, as a cue sheet or playlist names its tracks and Discs), its file in each form (its `.7z`, its Compacted copy, a format its Emulator prefers less) and a save beside it, but not a loose cue sheet's tracks. It's the same ROM in the journal, with its Match. A name another ROM has in any case, in the ROM folder or the journal (a missing one included), or one its ROM folder wouldn't read back, is refused with nothing moved; a name differing only in case is still a rename.
- **Add ROM** ([#50](https://github.com/danielholmes/ludeum/issues/50); `AddROM`, `ROMSource`): the toolbar's upload button, beside Add Game, asks for a ROM from anywhere: its file (a cue sheet brings its tracks, a playlist its Discs), a `.7z` or `.zip` of it, its folder, or each of its Discs. The Platforms whose ROM folders read it are worked out first (an archive by its listing; a folder or several Discs only where ROMs are kept in subfolders); none is an error. Then the IGDB search, its Platform filter limited to those Platforms (set when there's one), and a result's Platform chip chooses the Game; a Platform that doesn't read it is refused. Last, where it goes and what's done to it, **Copy them** or **Move them** (remembered), and, on a Platform whose ROMs can be Archived, **Archive it once it's in** (remembered). It runs as a Background task, and the Game opens once it's in.
  - **What's done:** it's put in the form its Platform keeps, named after the ROM (its file's or folder's name; several Discs, Disc 1's without its Disc). A Compactable Platform's ROM is Compacted, its game renamed after the ROM inside; an archive its Emulator already opens goes in as it is. A Platform that keeps ROMs in subfolders gets `<ROM name>/`, with a playlist written for Discs that have none (where its Emulator reads playlists). Anything else is one Playable file, `<ROM name>.<ext>`. An archive is unpacked first. An Added ROM goes in Playable; when Archive it once it's in is on, its Archive is queued as its own Background task once it's recorded. More than one image that isn't Discs is refused as unclear.
  - **Safely:** everything is copied (a clone on APFS) or unpacked into `.ludeum-work` in the ROM folder and moves into place only once it's all there and, for a Compact, tested and its listing checked. Then the ROM folder must read it as a Playable ROM in one form, or it's taken out again. It's recorded (with its checksum) and Matched as manual in one transaction; a failure there takes it out of the ROM folder too. Only then do moved files go to the **Trash**. A ROM whose name has no region tag has its Regions looked up last.
  - **Refused, with nothing touched:** a ROM of that name already in the ROM folder, or a missing ROM of that name that's another Game's (delete it there first). A missing ROM of that name that's the same Game's, or unmatched, comes back instead of a new one. An Import that read the new file before it was recorded leaves it as Add ROM recorded it.
  - **Several at once** (`ROMSource.split`, `AddROMsSheet`): picking more than one ROM in the same panel Adds them one at a time. The picked files are split into ROMs: each folder and archive is one, and so is each other file less any that another brings (a cue sheet's tracks, a playlist's Discs), with the Discs of one Version together unless no Platform reads them that way (GameCube's stay apart). A stepper takes me through them: "ROM 2 of 5", Previous and Next, and a strip of every ROM marked with what became of it (Added, without a Match, skipped, can't go in), any of which opens it. Each ROM gets the same search and confirmation as one picked alone, the search already run on its name; Add ROM queues it as its own Background task and moves on to the next ROM not done with, closing once all are. Instead, **Skip** leaves it out, and **Add without a Match** (on its likeliest Platform, else one chosen from those that read it) puts it in for an Import to add as a ROM and Match, automatically when the checksum and name agree, else from the Review queue. Those without a Match, and skipped ones, can be undone. Once every ROM is done with, a last step lists those without a Match, with **Copy them** or **Move them**, and puts them in together as one Background task (Cancel leaves them out, though the ROMs already queued still go in), each made and checked as one is but not recorded (one refused is left as it was, and the rest still go in, the task failing with which and why), and once it ends (failed or cancelled too) an Import adds those that went in as ROMs, and only those, its summary listing those it Matched automatically and those back on their Game. Should that Import not run (Ludeum quit first), they wait as Stray files. A ROM no Platform reads, or whose name its ROM folders all have already, says why and is passed over, and two picked ROMs can't go in under one name on one Platform.
- **Background tasks** panel at the foot of the sidebar: hidden when idle, one line while busy ("Archiving ICO · 42%", plus waiting and failed counts), and opened, each task with progress and Cancel; failures stay until dismissed. Tasks run one at a time and keep going on other screens. The launch cache refresh shows here too. Quitting while tasks are queued or running asks first. While any are queued or running, the **Dock icon** (`DockTileProgress`, `BackgroundTasks.overallProgress`) has a bar across its foot of how far they've got together, every task since none were last queued or running an equal share (those that have run, however they ended, in full; the running one as far as it's got; queued ones not at all), and a badge of how many are queued or running; it goes back to the plain icon once none are. The cache refresh isn't counted.

### Attachments
- **An Attachment is any file about a Game** (a manual, a map, a guide, a save), never a copy of the Game itself: an image of a game no Emulator Plays yet is a ROM. A Game can have any number, Owned or not. Any of them can be marked a **Manual**, as many as I like.
- **The journal owns them; the files live in the Data folder** ([ADR 0014](adr/0014-attachments-are-journal-owned-files-in-a-readable-folder.md)), under `Attachments/<Platform>/<Game name>/`, each keeping its own file name. The Platform's folder is its ROM folder's name where it has one (`SNES`), else IGDB's name (`PC (Microsoft Windows)`). Names are made file-safe as a Standard name is (`Half-Life 2: Episode One` is `Half-Life 2 - Episode One`). A Game sharing its name with another on its Platform, or with a folder already there, gets `<Game name> (2)`. A Game with no Attachments has no folder: the last one deleted takes its folder, and its Platform's if that's empty, with it. Files I put in `Attachments/` myself are ignored.
- **The folder follows the Game.** After its name or Platform changes, its folder moves to fit, when its page next loads or at the next Import; a folder whose name still fits, with or without its suffix, stays. A folder that isn't there (Dropbox still syncing) is left until it is.
- **Game detail:** an **Open Manual** button under the Game's name, beside the Expansion lines, opens its Manual in the app the system uses for it, or offers a menu when it has several; there's none when it has no Manual. An **Attachments** section after Copies lists them, Manuals first, then by name: each opens with a click, with Show in Finder (or **Locate…** when missing) and a menu of Mark as Manual / Not a Manual, **Rename…** and **Move to Trash…**.
- **Adding:** **Add Manual…** and **Add Attachment…** pick any number of files (never a folder: zip it, or make it a PDF, first; nor a file already in `Attachments/`), or files are dropped on the section. A sheet confirms them, whether they're Manuals (on from Add Manual) and whether they're copied or moved; moved originals go to the Trash once they're in. A name already in the folder gets ` (2)`.
- **Renaming** keeps the extension (typed again, it isn't doubled) and renames the file. A name another of the Game's Attachments, or another file in its folder, has is refused; changing only its case is fine.
- **Deleting** sends the file to the Trash after a confirmation; a missing one just leaves the journal.
- **Missing files:** an Attachment whose file isn't there is marked missing when its Game's page loads or an Import runs, shown crossed out, and waits in the Review queue under Missing Attachments until the file comes back, I Locate it, or I delete it.

### Covers
Decided on [Map: Game images](https://github.com/danielholmes/ludeum/issues/40). Why Box art comes first: [ADR 0006](adr/0006-box-art-before-igdb-cover-art.md); why it comes only from LaunchBox: [ADR 0020](adr/0020-launchbox-is-the-only-source-of-box-art.md).

- **Which image a Game shows:** my upload, else LaunchBox Box art, else the first Bundle's Cover (Bundles), else IGDB's Cover art, else a placeholder. Every Game looks for its Box art by title, with ROMs or none, whether or not its Platform has a ROM folder; nothing about it is kept in the journal, so it's worked out each time the Cover is shown, and renaming a Game, changing its IGDB link, Matching a ROM or editing a Copy's Regions changes it with no step to rerun. A Playthrough's Version never affects the Cover.
- **Game detail** shows the Cover in its own shape (SNES boxes are wide), at the top of the column beside the Game's name and Play; clicking opens it full size. Below IGDB's Screenshots, LaunchBox's have their own section, "LaunchBox Screenshots", found the same way as its Box art: title screens then gameplay shots, of the one game matched, shown as IGDB's are (the same tiles, "+N more", and the gallery, where a small one is scaled up by a whole amount). Each section's tiles are its Platform's screen's shape (`ScreenshotShape`), the one most of IGDB's Screenshots are for the Platforms with many, so a tile shows a whole one: 10:9 for Game Boy, Game Boy Color and Game Gear, 3:2 for Game Boy Advance, 16:15 for NES and Famicom, 8:7 for SNES and Super Famicom, 10:7 for Mega Drive and Sega CD, 16:10 for DOS and Amiga, 4:3 for the TV Platforms before widescreen (PlayStation, PlayStation 2, Nintendo 64, GameCube, Saturn, Xbox, Master System, PC Engine CD, MSX2), 2:3 for Nintendo DS (both screens, one above the other), and 16:9 for every other Platform and the IGDB screen, whose results have no one Platform; any but a 16:9 one is cropped from IGDB's original, as its thumbnails are cropped to 16:9. They fill the width exactly in two rows of the biggest that keep them at most 300 points tall, so a wider panel fits more across (a Game Boy's four across 600 points, 266 tall; 16:9 two across a narrow panel, three across 600), though never more than four, taller instead (a Game Boy's and an NES's in the widest Game detail), or, when those would be under 100 points wide (Nintendo DS), in one row of as many as bring each screen nearest 12,000 square points (four across 600). There's no section while they're looked for or when LaunchBox has none, and "Couldn't load" when they can't be.
- **LaunchBox Games Database** ([ADR 0018](adr/0018-launchbox-box-art-after-libretros.md)): a Game looks in LaunchBox by title, on the LaunchBox platforms its Platform maps to (Super Famicom to SNES, PC to Windows, Windows 3.x and MS-DOS, where LaunchBox files the PC games from before Windows 95: its Windows Syndicate is only 2012's reboot). Its names are the one it shows, IGDB's and its own; a LaunchBox game's alternate names count too. Names match by title key: the text before the first tag, with the article at the start or end of a title and of its subtitle ignored, wherever No-Intro (`Legend of Zelda, The - Spirit Tracks`), GoodTools (`Legend of Zelda - Spirit Tracks, The`) or IGDB (`The Legend of Zelda: Spirit Tracks`) puts it, `&` and `_` read as "and", and accents dropped; only once no name matches that way is each tried with umlauts and macrons spelled out (Einhänder as `Einhaender`, Ōkami as `Ookami`), and then by loose title key, with "a", "an", "the", "and" and "in" dropped wherever they are, as one name can keep small words another leaves out (`Spider-Man and the X-Men in Arcade's Revenge` is `Spider-Man - X-Men - Arcade's Revenge`). Only once none of those finds a box are IGDB's alternative names for it tried: they reach names IGDB writes differently (Commander Keen in Invasion of the Vorticons: Marooned on Mars is `Commander Keen 1 - Marooned on Mars`), but can be a working title another game has (Command & Conquer: Renegade was Commando), so a box for the Game's own names always wins. Matches are accepted silently; a wrong one is fixed by uploading. Of several matches, a game's own name beats another's alternate name, then the game released closest to IGDB's year for the Game (Doom in 1993 or 2016; a regional release or port a year or two off still beats a reboot of the same name; one with no year comes last), then the box for its Copies' Regions (its ROMs' included), else North America's, the World's, one with no region, Europe's (a European country, Australia or Oceania), Japan's; then the shortest name, then the first in the dump. LaunchBox's whole database is one dump, `gamesdb.launchbox-app.com/Metadata.zip` (about 110 MB, 575 MB unzipped, remade daily). The launch refresh downloads it to a file and reads it, last, when there's none or the last was read more than 30 days ago: streamed out of the zip by `/usr/bin/unzip` without unpacking it, it keeps each game on a mapped platform that has a Box - Front or a Screenshot (a title screen or gameplay), with its names (and their title keys), year and those images' file names and regions, about 73 MB in `cache.sqlite`, replacing the last all at once. One that can't be downloaded or read leaves the last in place and is tried again a day later, not at every launch, and says so in an alert: what went wrong (not downloaded, or downloaded but not readable, as when LaunchBox changes its format) and what Box art shows meanwhile (the last dump's, with when it was read, or what it would without LaunchBox). Nothing else the refresh does is an alert. Images come from `images.launchbox-app.com` by file name, cached the first time they're shown. Changing what's kept changes the cache entry that says when the dump was last read, so the next launch reads it again.
- **libretro-thumbnails** was the first source of Box art, by ROM file name, until LaunchBox replaced it ([ADR 0020](adr/0020-launchbox-is-the-only-source-of-box-art.md)). The cache's `v5` deleted its listings and images.
- **IGDB:** each linked Game's Cover art (`cover` `image_id`, `cover_big_2x`) and Screenshot ids stay on its cached record. Cover art is the last fallback above; Screenshots and Cover art are stored for showing elsewhere later.
- **Everything but uploads lives in the cache,** unbacked, downloaded the first time it's shown (a placeholder until then). A wiped cache downloads it again.
- **Uploads** are allowed on any Game, and win over everything. They're stored in the journal database as BLOBs (backed up, deleted with the Game), normalised on the way in: decoded, shrunk to fit a 1,200 px long edge (never enlarged), re-encoded as JPEG at quality 0.9. Anything macOS can decode, by file picker or drag-and-drop. Removing an upload falls back down the order.
- **OpenEmu's Box art is no longer a source** ([ADR 0009](adr/0009-ludeum-reads-rom-folders-openemu-is-gone.md)): `migrate-openemu` deleted its cached copies, and a Game whose only Box art was OpenEmu's shows IGDB's Cover art until I upload one.

### External data and cache (built: `LudeumCore`)
- **IGDB** (Twitch app token): the full game record, with every useful sub-record expanded plus time-to-beat. Fetched in batches of 100 (halved if IGDB answers 413). One request per name search, since multiquery ignores `search`. At most 3 requests a second.
- **Hasheous:** MD5 or CRC32 → IGDB game and platform, and the DAT entry's name and countries (for a ROM's Regions). "Not found" is cached. At most 1 request a second. An optional app key can be set with `HASHEOUS_API_KEY`.
- **Cache:** in `~/Library/Caches/Ludeum/`, shared by the app and `ludeum-import`. Entries keyed as `source:kind:id`, fresh for 60 days. An expired entry is still used if refreshing it fails, and what a screen is waiting on (a Cover, the Library's facts, Game detail) uses an expired game record as it is, without asking IGDB: the launch refresh fetches it again. Only successful answers are cached. Images never expire. In memory, Covers are kept decoded at the Library's current tile size up to a limit, and the full image is read only when one is enlarged. Runs can be interrupted and resumed.

### Playing in an Emulator
Each Platform's Games play in a standalone Emulator (ADR 0008), from the ROM's ROM folder.

- **Emulators** are hard-coded per Platform in `Emulator.of(platformId:)`, not settings: MesenCE for NES, Family Computer, SNES, Super Famicom, Game Boy, Game Boy Color, Game Boy Advance, Master System, Game Gear, PC Engine and PC Engine CD; DuckStation for PlayStation; Dolphin for GameCube and Wii; ares for Nintendo 64, Mega Drive/Genesis and Sega CD (with `--system` naming which); melonDS for Nintendo DS; PPSSPP for PlayStation Portable, from a copy of its `ppsspp.ini` with its lowest-latency display settings for every Game (`InflightFrames = 1`, `LowLatencyPresent = True`, `FrameSkip = 0`; PSP emulators have no run-ahead), passed with `--config=`. Not `--appendconfig`, which saves into PPSSPP's own file. PCSX2 for PlayStation 2, launched `-batch -fastboot -gamecfg <file> -- <rom>`, where the file is Ludeum's game settings with Optimal Frame Pacing (`[EmuCore/GS] VsyncQueueSize = 0`) for every Game. It stands in for PCSX2's own per-game settings; its main settings (controllers, BIOS, renderer) still apply. xemu for Xbox, launched `-dvd_path <rom>` with no settings: it has no run-ahead, its one latency setting (VSync) stays its own, and its boot ROM, BIOS and hard disk image are set up in xemu. Game Boy and Game Boy Color Games have a **Game Boy Model** setting (Auto, Game Boy, Game Boy Color, Super Game Boy), passed to MesenCE as `--gameboy.model=` (Auto is `AutoFavorGbc`); every model is offered whatever the ROM supports.
- **Play** (Game detail only) opens the Game's present ROM in its ROM folder: the multi-disc playlist, else the first present ROM. A ROM whose Discs have no playlist is refused, since the Emulator couldn't change Disc: "Its Discs have no playlist: put an .m3u naming them in its folder, and it's seen at the next Import". That's a subfolder holding its Discs (two or more cue sheets, or with none images, each a different `(Disc N)`) but no `.m3u`, on a Platform whose Emulator reads playlists (elsewhere the folder just opens at Disc 1); Import keeps it as a ROM opening at Disc 1 and flags it (`needsPlaylist`), and a playlist put in by hand clears that at the next Import. Add ROM always writes one, so only a folder put in by hand, then Added as a Stray file, can lack it; the Review queue's No playlist kind, and its Make playlist, went for that reason. An Xbox ROM that's a full Redump image, its game partition (whose media header is 64 KiB in) starting 387 MiB in rather than at the start (`XboxDisc`), is refused, as xemu would only reach its dashboard: "It's a full Redump image, and xemu boots only an XISO: make one with `xdvdfs pack`, then put it in its place." One that's neither goes ahead, and so does one kept online only, as reading it would download it all. A PlayStation Game with DuckStation settings of its own is refused when its ROM's Disc 1 has no Serial, as its per-game file can't be named ([ADR 0021](adr/0021-duckstation-settings-go-in-its-per-game-file-named-by-the-discs-serial.md)): "Its Serial hasn't been read yet, and its own DuckStation settings need it: it's read at the next Import. Set them back to Default to Play meanwhile.", or "Its Disc has no Serial DuckStation can use, so it can't have DuckStation settings of its own: set them back to Default to Play.", or for a `.chd` or `.pbp` "Its Serial can't be read from a .chd yet, so it can't have DuckStation settings of its own: set them back to Default to Play."; one with none Plays regardless. A PlayStation Game is also refused while DuckStation is open ("DuckStation is open. Quit it, then Play: Ludeum writes its settings before each Play, which an open DuckStation would write over."), while it's being installed, and until it's installed ("DuckStation isn't installed. Install it from Ludeum ▸ Emulators…"). It never changes journal data. A running MesenCE gets the ROM in its open window; DuckStation, Dolphin, ares, melonDS, Ymir and xemu open another window. A Game whose Platform has no Emulator shows "No ‹Platform› emulator yet" instead.
- **DuckStation is Ludeum's own copy** ([ADR 0024](adr/0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md)): not looked up by bundle identifier but installed by Ludeum into `Emulators/DuckStation.app` in the Ludeum folder, from **Install** (or **Reinstall**) in the Emulators… sheet, as a Background task (`DuckStationInstaller`): the pinned release's `duckstation-mac-release.zip` (`DuckStationRelease.pinned`: a versioned tag, its build and its zip's SHA-256 as GitHub's release API gives them, fetched from `stenzek/duckstation` else `duckstation/old-releases` once it has aged off the first thirty) is checked against the digest, unpacked with `ditto` and its quarantine taken off, checked for its build with `-version`, given a `portable.txt` beside its executable (so its data root is its own `Contents/MacOS`, shared with no other DuckStation), and swapped into place, carrying across whatever the copy it replaces kept in its data root (`settings.ini`, play time, its caches); then the Standing settings are written. Nothing is replaced until the new copy checks out, and Install is refused while DuckStation is open. A bump is the tag, build and digest in code. Rolling tags can't be pinned: their zip is replaced on every build.
- **Emulator versions** are checked once per launch, in the background, for every installed Emulator (`EmulatorVersions`, `EmulatorVersionChecks`). Each has an expected (minimum) version, the one its launch code was written against, kept with its definition: MesenCE 2.2.1, Dolphin 2609, ares 148, melonDS 1.1, Ymir 0.3.3, PPSSPP 1.20.4, PCSX2 2.9.103, xemu 0.8.136. DuckStation's is exact, build 12442, the one Ludeum installs (the rolling release as it stood on 2026-10-25, until a versioned release past it: #90): any other build is "Wrong build: install again", and Play is refused until it's installed again, as it is for a copy in the Ludeum folder that isn't portable; it's checked again after each Install. The version comes from the command line where the Emulator has a version flag and its app version isn't the real one (PCSX2 and DuckStation `-version`; PPSSPP and ares `--version`), else the app's version (melonDS, Ymir, Dolphin, xemu; Ymir's `--version` opens its window, and xemu's `-version` is QEMU's), else for MesenCE (whose app version is a placeholder) the `Version` its settings file records. DuckStation compares by build number.
  - **Older than expected:** Play is refused: its button is red, the reason shows under it, and pressing it says so in an alert.
  - **A newer major version**, or **a version that can't be read:** an alert the first time that Emulator is Played in the launch, then Play goes ahead. Dolphin (year-month), ares and DuckStation (single counts) have no meaningful major, so they're never warned about being newer. An Emulator installed or updated while Ludeum is open is checked at the next launch; until the launch check finishes, Play goes ahead unchecked.
  - **Emulators…** (app menu, under Settings…) opens a sheet listing every Emulator: whether it's installed, its status from the launch check (OK, too old, wrong build, newer major, unreadable, checking, or installing with how far it's got), the version Ludeum needs against the one installed, and the Library's Platforms it plays, with Open beside each one the check found installed to open it with no ROM, even one too old to Play, and Install or Reinstall beside DuckStation. Open gives DuckStation its Standing settings first, unless it's open already.
- **Emulator settings:** run-ahead frames, 0–10, stored as `game.runAheadFrames` (null is the default, 0), and for Game Boy and Game Boy Color Games the Game Boy Model, stored as `game.gameBoyModel` (null is Auto), and for PlayStation Games the CD read and seek speedups, stored as `game.cdReadSpeedup` and `game.cdSeekSpeedup` (null is DuckStation's own setting). Every Play passes the full set, and never changes the Emulator's own saved preferences, so one Game's settings never carry into the next; DuckStation's go into its per-game file instead, where a Game with no run-ahead of its own has DuckStation's:
  - MesenCE: `--doNotSaveSettings --emulation.runAheadFrames=N`, plus `--gameboy.model=M` for Game Boy and Game Boy Color Games.
  - DuckStation takes no settings on its command line (it dropped `-settings` in build 8843), so Ludeum writes its files ([ADR 0024](adr/0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md)). Before every launch Ludeum gives it, Play and Open alike, and after each Install, the **Standing settings** go into its own `settings.ini` (`DuckStationSettings.writeStanding`), the file left alone when it already says so: every folder worth keeping as an absolute path into the Data folder (`[Folders] SaveStates`, `GameSettings`, `InputProfiles` and `Screenshots`, `[MemoryCards] Directory` and `[BIOS] SearchDirectory`, each `Emulators/DuckStation/<Name>/`, made then), `[AutoUpdater] CheckAtStartup = false` (DuckStation would replace its own bundle), and for every Game fast boot and the lowest input latency: `[BIOS] PatchFastBoot = true` skips the BIOS logo and `FastForwardBoot = true` runs unthrottled to the game's first frame, written rather than passed as `-fastboot`, which would override DuckStation's game database turning fast boot off for the games it breaks (`ForceFullBoot`: Lomax, Nightmare Creatures and a few more), and fast-forwarding has no flag anyway; `[Display] OptimalFramePacing = true` presents each frame at a steady interval, and `PreFrameSleep = true` (which needs it) waits to run each frame until just before it's shown. Everything else in the file is DuckStation's own, set in its UI; a Standing one changed there lasts until the next launch. They're only written while DuckStation isn't open, since it rewrites the file whole from memory on any change. Then a Play merges the Game's own settings into DuckStation's per-game file for the disc, `<Serial>.ini` in the Data folder's `Game Settings`, as its Game Properties does ([ADR 0021](adr/0021-duckstation-settings-go-in-its-per-game-file-named-by-the-discs-serial.md)), and opens the ROM with `-- <rom>`. The Game's `[Main] RunaheadFrameCount`, `[CDROM] ReadSpeedup` and `[CDROM] SeekSpeedup` are set where it has them and taken out where it hasn't, so DuckStation's own applies; the file's other settings stay, a section left empty goes, and a Game with none of its own and no file yet gets none. What every Play wrote before ADR 0024 (the Standing keys on, and card 1 as the shared card Ludeum named in the Data folder) is taken out as it's met, but not a value set since in Game Properties (fast boot off, a card of my own). A multi-disc Version's file is Disc 1's, as DuckStation's is; when that sets `[Main] UseSeparateConfigForDiscSet = true`, every Disc's is written. DuckStation's game database still turns each speedup off for the games it knows it breaks.
  - ares's run-ahead is only on or off (one frame): its Games choose Off or On, stored as 0 or 1, and passed as `--setting General/RunAhead=true|false`, which ares doesn't save.
  - Dolphin has no per-Game settings: every Play turns on Rush Frame Presentation and Smooth Early Presentation for that launch (`-C`) to lower input latency, leaving Immediately Present XFB off since it breaks some Games.
  - melonDS and Ymir have no per-Game settings and no run-ahead: Play just opens the Game.
- **Save states** ([ADR 0024](adr/0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md)) are DuckStation's, made and managed in its menus and kept, as its Standing settings say, in `Emulators/DuckStation/Save States/` in the Data folder, as `<Serial>_<slot>.sav`, `<Serial>_resume.sav` and `<Serial>_<slot>.bak` (the Previous one). Nothing is copied: DuckStation writes each under another name and renames it into place, so Dropbox never sees half of one.
  - **Game detail** has a Save states section for a PlayStation Game whose ROMs' Serials are read: each state by Disc (when there's more than one), then Resume, then slot, its Previous one after it, with its screenshot (shown 4:3), its title ("Resume", "Slot 3", "Slot 3 (previous)") and when it was saved, read again when Game detail opens and whenever Ludeum becomes active. **Play** from one opens `-statefile <state> -- <rom>` with the Game's settings; it's refused as Play is. **Delete…** sends it to the Trash. **Show in Finder** shows the file.
  - **Screenshots** come from the state's header (DuckStation's `SAVE_STATE_HEADER`, version 69 on): RGBA, uncompressed, Deflate or XZ, or Zstandard (DuckStation's default), which needs `zstd`, an optional system tool (`brew install zstd`). Without it, or for an older state, a state has a blank tile.
- **Memory cards** ([ADR 0024](adr/0024-ludeum-installs-duckstation-and-says-where-it-keeps-things.md)): DuckStation names and manages them; Ludeum only says where, `Emulators/DuckStation/Memory Cards/` in the Data folder (its Standing `[MemoryCards] Directory`), and shows them. DuckStation writes a card whole under another name and renames it into place, a few seconds after the game saves.
  - **Which card is a ROM's:** the one card 1 has by its per-game file's settings over its `settings.ini` (`[MemoryCards] Card1Type`, `Card1Path`, `UsePlaylistTitle`, `Directory`), as DuckStation names it. By default (`PerGameTitle`) that's `<title>_1.mcd`, the title the disc's `saveName`, else `name`, in the `discdb.yaml` bundled in DuckStation's app, or its disc set's in `discsets.yaml` unless a card of the disc's own is there already, or for a disc it doesn't know (or without DuckStation) the file Play opens; `/`, `*`, `:` and control characters become `_`. `PerGame` is `<Serial>_1.mcd`, `PerGameFileTitle` the file's name, `Shared` its `Card1Path` (or `shared_card_1.mcd`); `None` has none. A title given in DuckStation's game list isn't looked for.
  - **Game detail** has a Memory card section for a PlayStation Game, one card for each of its present ROMs with a Disc 1 Serial, one per Serial (titled by the ROM's name when there's more than one): when it was saved, Show in Finder, then each Card save on it, in the card's own order, with its icon (16 × 16, shown at twice that, its frames shown in turn), its title (Shift-JIS, full-width letters made plain) and its blocks, other games' Card saves included. With no card yet, "No saves yet". A card that can't be read as one (not 128 KB, or no `MC` header) says so; one with no Card saves says "No saves on it". It's read again when Game detail opens and whenever Ludeum becomes active. There's no delete: a card stays in the Data folder when its ROM goes, listed nowhere.
  - **Moving over, once, by hand,** on 2026-10-28: `scripts/migrate-duckstation.sh` moved what DuckStation kept in `~/Library/Application Support/DuckStation` into the Data folder and the installed copy's data root, and `ludeum-import duckstation-cards` gave each `<Serial>.mcd` DuckStation's name for that disc's card, setting the older aside as `… (older).mcd` where both were there, and took out of each per-game file what every Play used to write. Both went once they'd run. Then `Data/Emulators/DuckStation/` is marked "Make available offline" in Dropbox by hand, as DuckStation reads with plain file calls and would stall on an evicted file.

### What to play next and Top-rated
- **What to play next** is a plain view, with no ranking or suggestions. It has three sections: **Playing**, **Up next** and **Backlog**. Each Game appears once, in the first section that fits (a Game that's Playing and Up next shows under Playing).
- **Sorting:** the same filter and sort controls as the Library. Up next and Backlog default to when the Intent was set, newest first, with undated Intent after every dated one, by name. Playing defaults to the in-progress Playthrough's start date, newest first (a Game's latest start counts if several are in progress). Name order is available too. "Intent set" is also a Library sort, with Games that have no Intent last.
- **Start playing:** an action on a Game in Up next or Backlog. In one step it creates an in-progress Playthrough starting today (day precision) and clears the Game's Intent.
- **Top-rated** is one list of every rated Game, by current Rating, highest first, with no top-N cut-off. It has the same filters as the Library (Platform, Childhood), so "per Platform" is the Platform filter.
- **Ties share a rank** (1, 2, 2, 4) and are listed by name. There's no hidden tie-break.
- **Unrated Games never appear.** A Rating of 0.0 is a real Rating and appears. Rating history plays no part.

### Face-off
Checking my Ratings against each other, two rated Games at a time. My current Ratings are the starting belief, so pairs go where they're most likely wrong, and I can stop at any point.

- **A Battle** shows two Covers, with each Game's name and Platform underneath and never its Rating: "Which did you like more?" ← or → picks one, ↓ is About the same, Space skips (no Battle; the pair stays away for the day and its Games are offered less) and ⌫ undoes the last pick, one level, showing its pair again. Every rated Game takes part; a Game that becomes unrated sits out but keeps its Battles.
- **While I battle** the Disagreements tab shows their count, and a line under the pair counts today's Battles. Picking a Disagreement shows its Game's detail, but the Battles tab clears it, so no Rating is ever beside a pair. Battles, skips and Keeps are journal data, so Backups hold them.
- **Battles count less with age:** half after a week, a quarter after two (by local day, like Ratings). A pair isn't fought again within 14 days.
- **Choosing pairs:** chase the most doubtful suspect (a Game an Upset has put in doubt, or a Disagreement with no Battle on the far side yet) with the opponent that would say most about it, at most 6 Battles a day each; otherwise cover the Games with least evidence first. Every 8th pair of a day is two Ratings at least 2.0 apart, to catch big errors. There's no "done": a sitting of 25 finds about one real problem, so it's a slow, continual check.
- **The model** (`FaceOffModel`): each Game's place on the Rating scale, believed before any Battles to be its Rating ± 0.5; Bradley–Terry on the Rating scale for a win (0.4 points of noise), a pull together for About the same. A Disagreement is a Game whose place is at least 1.64 standard deviations from its Rating and rounds to a different one. Its placement comes from its Battles alone, against its opponents' Ratings: "belongs around 7.0–7.5", always on the side of its Rating the Battles point to, or only "below 8.5" (the lowest Rating it lost to) until it has a win or About the same; "above" likewise. Tuned against a simulated me on branch `prototype/face-off`.
- **Disagreements** are a tab beside Battles, biggest gap first then the surest, each with its placement and its Battles (newest first, with how much each still counts). **Set Rating** (prefilled with the middle of the placement) is an ordinary Rating change; **Keep** sets it aside until its Game fights another Battle. Battles outlive a Rating change.

### Year in review
A nice-to-have: built after the rest of v1 works.

- **One year at a time**, chosen from a picker listing only years with something in them. The current year is labelled "so far". The Library's filters (Platform, Childhood) apply.
- **Sections:** **Finished** and **Dropped** (Playthroughs that ended that year, with the Game's Cover, Rating and Platform); **Also played** (Playthroughs active that year that didn't end in it); and **summary numbers** (Finished, Dropped and Started counts, a per-Platform breakdown). Rating history and Childhood play no part.
- **Which years a Playthrough counts for:** every year from its start year to its end year (to the current year while in progress). It's under Finished or Dropped in its end year and under Also played in each year before that. Every Partial date has a year, so precision doesn't matter here.
- **Missing end date:** an ended Playthrough with no end date counts in its start year under Finished or Dropped, marked "end date unknown".

### Backups
- **When:** before every Import that changes ROMs, before schema migrations change an existing journal, before every deletion of a Game or Playthrough, and otherwise at most once a day (on launch, or the first change of the day). There's no undo, so the backup just before a destructive step is the one that matters. "Back up now" is in Settings.
- **How:** SQLite's backup API, written under a temporary name and then renamed, so Dropbox never syncs a half-written file. The cache isn't backed up.
- **Where:** `Backups/` in the Data folder, so into Dropbox through its link; not a setting. There's no extra local copy and no local fallback: it would sit at the same missing path, so without the Data folder a backup fails, and the step it guards with it (the app is blocked by then anyway).
- **Names:** dated, plus the operation that triggered them, e.g. `2026-10-02T1430-before-import.sqlite`.
- **How many are kept:** every backup from the last 7 days, then one a day for 30 days, then one a month forever. The database is a few MB, so this costs little and still covers a mistake noticed weeks later. The `before-migration` and `before-recovery` backups, with their move logs, are never pruned.
- **Restore:** "Restore from backup…" in Settings lists the backups. It backs up the current state first, copies the backup into the journal with the backup API (rather than swapping files under an open WAL database) and relaunches. Only the journal changes.

### Storage stats
- **Storage Stats…** (app menu, under Emulators…) opens a sheet of how much room everything takes, measured from the files each time it opens and again on Refresh; nothing is stored. Sizes are logical, so a file Dropbox keeps online-only counts in full. Hidden files are left out.
- **Data folder:** a row per Platform with a ROM folder, Platforms shown as one (SNES and Super Famicom, NES and Famicom) sharing a row, largest first: its Total (everything in its ROM folder), ROMs (present, "+N missing" from the journal), Playable and Archived (each a size and count), Not compacted (a count, on Platforms with a ready archive) and Not a ROM (what no ROM is made of). Zero cells are blank. A row with ROMs kept in both forms is marked (they're resolved in the Review queue); both copies count. A ROM folder that's absent or empty has no row; one that can't be read says so. Then Backups, Battery saves and the Data folder's subtotal: what Dropbox holds.
- **Attachments:** one row, everything in `Attachments/`, counted in the Data folder.
- **Outside it:** the journal (with its WAL), the cache, and the grand total.

### Settings and credentials
- **Settings screen:** IGDB credentials (client ID and secret) with a "Test connection" button (the same check as `ludeum-import check`), an optional Hasheous key, where the Data folder is (shown, with Show in Finder; not changeable), and the backup folder (shown) with "Back up now" and "Restore from backup…". No location is a setting.
- **IGDB credentials** are kept in the Keychain, along with the cached Twitch app token. If there are none at launch, Settings opens with a link to the Twitch developer console. This depends on a stable signing identity: without one, every rebuild asks for Keychain access again (see the packaging research).
- **Hasheous key: not requested.** Hash lookups don't need one. The key unlocks Hasheous's metadata proxy, which we don't use, and its rate limits aren't published. There's an optional field (Keychain) in case anonymous lookups get throttled. `HASHEOUS_API_KEY` stays for the CLI.

### Review queue
- **Layout: three panes, Mail-style** (chosen from three variants on `prototype/review-queue`). A sidebar lists the item kinds with counts: Unmatched ROMs, Duplicate Versions, Missing ROMs, Old missing ROMs, In both forms, Not compacted, Missing Attachments, Stray files. The middle column lists that kind's items (for Unmatched ROMs, the ROM name, then the suggestion, with a tick when the names agree, or "Search IGDB by hand"), and the right pane shows the selected item with its actions.
- **Unmatched ROMs** are every ROM with no Match, by name: those an Import couldn't Match Automatically (a Stray file I Added, or a ROM Added without a Match) and those Split off a Game. They were four kinds (Names agree, Checksum suggestions, Name suggestions, No suggestion) for the first Import's hundreds; they're one now, as they come one or two at a time.
- **An item's detail:** the ROM name, its Platform and why it's here, then the suggestion with its cover, `game_type` and whether the names agree. For a related-record suggestion, the checksum's own game is shown crossed out above it.
- **Actions on a ROM item:** Confirm (when there's a suggestion), on the ROM's Platform, which its ROM folder gives it. Search IGDB… (the shared search from Adding Games), Assign to Game… (an existing Game, e.g. a fan translation; warns about Duplicate Versions), Make by hand… (the ROM's Platform pre-selected), and **Delete ROM…** (`LudeumStore.deleteROM`), which after a confirmation sends its files to the Trash and deletes it (a missing one just leaves the journal), as deleting a ROM does anywhere (see Deleting); refused, with nothing sent to the Trash, once it's Matched (it's deleted from its Game then) or when its files aren't in its ROM folder.
- **Duplicate Versions items** sit in the same three panes: the Game's present ROMs grouped by Version (a multi-disc Version's Discs together; each ROM by Version text and file name), a note that real exceptions need a code change, **Show Game** and **Check again**, which runs an Import. Each Version has:
    - **Keep only this Version**, after a confirmation: the other Versions' ROMs (subfolders whole, with any `.7z` or Compacted copy) go to the Trash and are deleted, Copy details and all, so they don't come back as Old missing ROMs. Everything is checked first: if the Game's ROMs have changed since they were shown, or a ROM's files aren't in its ROM folder, nothing goes to the Trash. If sending one there fails part-way, the ROMs already in the Trash are deleted and the rest stay.
    - **Split into its own Game**: the Version's ROMs lose their Match and wait under Unmatched ROMs, which opens at the first of them, to be Matched by hand (Search IGDB…, Assign to Game…, Make by hand…). Their files stay put, and the Game keeps its journal data. Search IGDB… on the Game's own IGDB game puts them back on it (no two Games share an IGDB link), so a separate Game needs another IGDB game (a re-release IGDB lists apart) or Make by hand. Until they're Matched, an Import that can now take a checksum for one (it had none) matches it again, and may Match it Automatically back to the Game. Refused, changing nothing, if the Game's ROMs have changed since they were shown.
    - Both are disabled while a Background task is queued or working on one of the Game's ROMs.
- **Missing ROMs items** are Games whose ROMs are all missing (not a Game with any present ROM, nor one with no ROMs). The item shows the Game's name with a button that copies it, and lists the Game's missing ROMs (Version text and file name), with **Add ROM file…** (or **Add ROM folder…** on a Platform that keeps ROMs in subfolders), **Delete its missing ROMs** (after which the Game is a plain journal entry, which Game detail can delete), **Show Game** and **Check again**. Add ROM there skips the IGDB search: the ROM is Added to the Game, its Platform must read it, and **Delete its missing ROMs** (on by default) deletes them once it's in.
- **Old missing ROMs items** are Games that still have a present ROM, with missing ones left over (a file renamed or replaced, then Added as a new ROM), listed with how many of each. The item shows the Game's present ROMs and its missing ones (Version text and file name), each missing one with **Delete**, then **Delete all** (or **Delete it** for one), **Show Game** and **Check again**.
- **In both forms items** are present ROMs, Matched or not, whose ROM folder keeps them in more than one form at once: a Playable copy beside an Archived `.7z` (PS2, PSP, Vita, or a `.7z` ares can't open on N64 or Mega Drive), or a loose file beside its Compacted copy. Each read of a ROM folder sees these forms of a ROM's name, not just the file a Play opens, and flags the ROM (`inBothForms`); any other loose file of its name isn't a form of it (it may be part of the ROM, as a playlist's Disc is) and is left alone. The item shows the copy that's kept and what goes to the Trash, each with its size, as the ROM folder has them now: the Compacted copy over a loose file or subfolder (smaller, and it still Plays; a subfolder goes whole), else the Playable copy over its Archived `.7z`. **Keep the Compacted copy** (or **Keep the Playable copy**) sends the rest to the Trash and the item goes; it refuses, with nothing sent to the Trash, when the copies have changed since they were shown. Nothing is ever removed automatically. Also **Show Game** (once Matched) and **Check again**. A copy removed by hand clears the item at the next Import.
- **Not compacted items:** every present ROM that can be Compacted, Matched or not: a loose file on a Platform with a ready archive, or an Archived `.7z` on N64 or Mega Drive. The middle column shows its file and what Compact makes of it; the detail explains, with **Compact** (and Show Game once it's Matched). Add ROM puts a ROM in Compacted, so only one put in by hand, then Added as a Stray file, waits here, and "Compact all N", for the backlog the move from OpenEmu left, went. Each shows its progress in place, and leaves the queue once its task finishes.
- **Missing Attachments items** are Attachments whose file isn't in their Game's folder, by Game then name: the middle column shows the file's name and its Game's, the detail has **Locate…** (choose the file wherever it is now; it's copied or moved back under the Attachment's name, a moved original going to the Trash), **Delete Attachment…** (after a confirmation) and **Show Game**. A file put back by hand clears the item once the Game's page opens or an Import runs.
- **Stray files items** ([ADR 0017](adr/0017-the-journal-says-which-roms-there-are.md)) are files in a ROM folder that aren't ROMs in the journal (kept in `strayFile`, by Platform and name), by Platform then name: the middle column shows the name and its Platform, the detail its file in the ROM folder, with **Add as ROM** (an Import that adds it, as a new ROM was always added: Matched automatically when the checksum and name agree, else waiting under its suggestion; its summary lists where it went), **Show in Finder** and **Check again**. When its Platform has missing ROMs, the detail lists them too, those whose titles share the most words with the file's first, then its Regions and Version (each with its Game), with **Give it this file** (`giveStrayFile`): for a file renamed in Finder, or replaced, the missing ROM takes the file and its name (and the Version text in it), staying the same ROM with its Match, Copy details and Playthroughs, where Adding it would make a new ROM and leave the old one missing; its checksum, its old file's, is dropped. "Add all N as ROMs", after a confirmation, adds every one listed (not a file that has turned up since). A file taken out of its ROM folder by hand clears the item at the next Import.

### Migrating from OpenEmu
Decided on [Remove OpenEmu entirely](https://github.com/danielholmes/ludeum/issues/51); why: [ADR 0009](adr/0009-ludeum-reads-rom-folders-openemu-is-gone.md).

- **`ludeum-import migrate-openemu`**, run once by hand on 2026-10-06 with Ludeum and OpenEmu closed, moved every OpenEmu ROM the journal had into its Platform's ROM folder in the Data folder, copied OpenEmu's Game saves unchanged into `OpenEmu Battery Saves archive/` there, and deleted OpenEmu's cached Box art, after a `before-migration` backup kept forever. Its 150 missing ROMs stayed missing, re-keyed by OpenEmu's file name.
- **`ludeum-import recover-openemu-renamed`** ([#72](https://github.com/danielholmes/ludeum/issues/72)), run once that evening after `into-folders`, brought in 111 of those whose files had been renamed after OpenEmu recorded them, after a `before-recovery` backup kept forever.
- Both went once they'd run, along with the main window's banner and Import's refusal while a journal still had OpenEmu ROMs, and Ludeum's own setting for where OpenEmu's library was.
- The Import page, the Sync page, Settings › OpenEmu, the sidebar's OpenEmu section and the Import when OpenEmu quits are gone, with nothing in their place.

### Disc ROMs into folders
- **`ludeum-import into-folders`**, run by hand on 2026-10-06 with Ludeum closed (twice, minutes apart), moved each loose ROM of the disc Platforms (PS1, Sega CD, Saturn, PC Engine CD) into a subfolder named after it, the way PS2's are kept, a playlist and the Discs it names into one, as one multi-disc Version. A `.7z` stayed loose beside its folder. It went once it had run (its `before-into-folders` backup is kept forever).

- `Matcher` (`LudeumCore`): the first-Import matching rules (Hasheous by MD5 or CRC32, names agree, Automatic vs suggestions, related records, excluded `game_type`s), Version text and Discs (`ROMName`), and Duplicate Versions. Tested at the `Matcher`, `namesAgree`, `ROMName` and `versions(of:)` seams.
- App skeleton: `project.yml` (XcodeGen), ad-hoc signed until the Personal Team id goes in the gitignored `App/Config/Local.xcconfig` (pending, a human step); no sandbox. The main window shell (sidebar, placeholder screens, Game detail pane) and the ⌘, Settings window. CI builds the app.
- Settings: IGDB credentials, the optional Hasheous key and the app's Twitch token in the Keychain (`KeychainSecretStore`, via `AppSettings`); "Test connection" runs `ConnectionCheck`. With no credentials at launch, Settings opens once with a link to the Twitch developer console. Credentials surviving a rebuild waits on the Personal Team id.
- Backups (`Backups`, `BackupName`, `backupsToPrune`): named by date and operation, written under a temporary name then renamed, into `Backups/` in the Data folder, failing without it; pruned in tiers; taken before deleting a Game or Playthrough and daily at launch; "Back up now" and "Restore from backup…" in Settings. The app now opens the journal. Also before every Import that changes ROMs, and before schema migrations run on a journal that has data (`before-schema-migration`, once per open). The one-off commands' backups (`before-migration`, `before-recovery`, `before-into-folders`, `before-into-bundles`) are never pruned. Still to hook up: the first change of the day.
- Adding Games (`GameSearch`, `IGDBClient.platforms()`, `platformPickerOrder`): the cached IGDB platforms list and the Platform picker (mine first); the one IGDB search with an optional Platform filter, add-on `game_type`s excluded in the query, Mods labelled, platform chips marked "In journal" and "Different platform…"; adding from a chip or by hand with the names-agree duplicate warning; "Link to IGDB…" for a hand-made Game, refused when the link is taken or it already has one. The app has Add Game. A Game added or linked doesn't take IGDB's Cover yet (Covers).

Game detail's Copies section lists the ROMs first, each with its Copy details on a line under its file, a pencil to edit them (`CopySheet`, without Kind or no longer owned) and a bin to delete it, then the hand-recorded Copies, Owned before Gone (dimmed and struck through) and each by when acquired, click to edit or right-click to delete, and **Add Copy…**; the sheet has the Kind, Regions as chips with a field to type one and a menu of suggestions, acquired on, acquired from, price and currency, and for a hand-recorded Copy the no longer owned toggle with gone on and gone to. Each ROM there is headed by its subfolder, when it's kept in one, else by its full file name, extension and all, and folds out to every file it's made of, named in full, with sizes ("3 files · 702 MB"): a cue sheet's tracks, a playlist's discs and their tracks (`ROMFiles`), or everything in a ROM folder ROM's subfolder (named from inside it), plus its `.7z`. An Archived or Compacted ROM's folded line adds how much room the archive saves against what's inside ("1 file · 390 KB (57% smaller)"), that in green, or in red when the archive is bigger ("(12% bigger)"), or "(online-only in Dropbox)" when it can't be read; opened, its `.7z` or `.zip` shows its compressed size and lists what's inside, each file at its uncompressed size.
